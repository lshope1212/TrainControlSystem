I want to modify the TrainControlSystem solution architecture to add a central WPF launcher application.

The purpose of this launcher is to serve as the entry point for the overall train-control system while preserving the fact that each subsystem WPF project is its own independently runnable executable.

IMPORTANT ARCHITECTURAL RULE:

The launcher must NOT absorb the other subsystem UIs into itself.

TrainModel.Wpf, TrackModel.Wpf, TrainController.Wpf, TrackController.Wpf, and CTC.Wpf must remain independent WPF executable projects.

The launcher should launch those applications as separate operating-system processes.

Do not convert the subsystem applications into UserControls inside the launcher.

Do not create project references from the launcher to the subsystem WPF projects merely for launching them.

--------------------------------------------------
RESPONSIBILITIES
--------------------------------------------------

The launcher should be responsible only for:

1. Displaying the available subsystem applications.
2. Allowing the user to launch an individual module.
3. Allowing the user to launch all available modules.
4. Displaying basic module status such as Running or Stopped.
5. Providing placeholder controls for future shared simulation timing:
   - System Time
   - Simulation Speed
   - Pause
   - Resume

Do NOT implement actual inter-process synchronization of simulation time yet.

Do NOT implement networking, named pipes, sockets, message buses, or other IPC yet.

The simulation timing controls should be clearly marked in the code as future integration points.

--------------------------------------------------
MODULES TO DISPLAY
--------------------------------------------------

The launcher UI should include entries for:

- Train Model
- Track Model
- Train Controller
- Track Controller
- CTC Office

Do not add MBO yet.

Represent the available modules using a model such as ModuleInfo rather than hard-coding all visual elements independently.

A ModuleInfo can contain simple properties such as:

- Name
- ExecutableName
- IsRunning

Add additional simple properties only if clearly useful.

--------------------------------------------------
PROCESS LAUNCHING
--------------------------------------------------

Create a small ModuleLauncherService responsible for launching module executables using System.Diagnostics.Process.

Use Process.Start with ProcessStartInfo rather than attempting to instantiate subsystem Window classes.

Conceptually:

Launcher.exe
    |
    +-- Process.Start --> TrainModel.Wpf.exe
    |
    +-- Process.Start --> TrackModel.Wpf.exe
    |
    +-- Process.Start --> TrainController.Wpf.exe
    |
    +-- Process.Start --> TrackController.Wpf.exe
    |
    +-- Process.Start --> CTC.Wpf.exe

Keep this service simple.

It should expose operations approximately like:

LaunchModule(ModuleInfo module)
LaunchAll(...)
IsModuleRunning(...)

If executable path resolution cannot yet be made fully robust because Visual Studio places each project into its own bin directory, implement the cleanest development-time approach and clearly document it.

Do not add deployment/install tooling yet.

Do not introduce complicated configuration systems yet.

--------------------------------------------------
IMPORTANT DEPENDENCY RULE
--------------------------------------------------

The launcher should NOT reference:

TrainModel.Wpf
TrackModel.Wpf
TrainController.Wpf
TrackController.Wpf
CTC.Wpf

as C# project dependencies simply to launch them.

The launcher treats them as separate applications/processes.

It may reference TrainControl.Common if genuinely useful, but avoid unnecessary references.

The architecture should remain:

Launcher.exe
     |
     | launches processes
     v

Subsystem executables

while subsystem code dependencies remain:

Subsystem.Wpf
     |
     v
Subsystem.Core
     |
     v
TrainControl.Contracts / Common

except for minimal DataContext setup if necessary.
