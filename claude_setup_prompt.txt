Please modify the CTC module's scheduling and Active Movement Plan functionality to support configurable **dwell times** at destination/stop blocks.

First, inspect the current CTC implementation and understand how:
- the Schedule Builder stores destinations and arrival times,
- schedules are converted into an Active Movement Plan when a train is dispatched,
- suggested speed and authority are calculated,
- station information is represented in the imported track/block data,
- active movement-plan timing is recalculated when a dispatcher changes an arrival time or destination.

Do not unnecessarily redesign the existing architecture. Add this functionality in a way that fits the current models, ViewModels, services, and UI patterns.

## Required behavior

Each scheduled destination/stop should now have a **Dwell Time**.

The default dwell time depends on the destination block:

- If the block contains a station: **45 seconds**
- If the block does not contain a station: **0 seconds**

The dispatcher must be able to override this value manually.

For example:

| Destination | Station? | Default Dwell |
|---|---|---:|
| Block A1 | No | 0 sec |
| Block C4 | Yes | 45 sec |
| Block D7 | No | 0 sec |

However, the dispatcher should be allowed to change any of these values, such as:
- station block: 45 → 60 seconds
- station block: 45 → 30 seconds
- regular block: 0 → 20 seconds

A dwell time of `0` means the train does not intentionally stop at that block.

Add an appropriate dwell-time property to the schedule/movement-plan model.

Prefer a strongly typed representation such as:


if that works cleanly with the existing architecture.

If the current project represents timing primarily using integer seconds, using something like:

Follow the existing conventions of the project rather than introducing unnecessary conversion complexity.

The important requirement is that dwell time is explicitly stored for each applicable schedule/movement-plan entry.


Do NOT scatter checks like this throughout the UI.

Put the logic somewhere appropriate in the CTC Core/service layer so both the Schedule Builder and Active Movement Plan can use the same behavior.

Use the existing track-layout/block model to determine whether a block contains a station.

Do not identify stations using hard-coded block numbers.

## Schedule Builder

Add a **Dwell Time** field/column to each Schedule Builder destination.

When the dispatcher selects or changes the destination block:

1. Determine whether the selected block contains a station.
2. Populate the default dwell time:
   - station = 45 seconds
   - regular block = 0 seconds
3. Allow the dispatcher to manually edit the value afterward.

Important:

Do not continuously overwrite a user-entered dwell time just because the selected block is a station.

The default should be assigned when the destination is initially selected or changed.

For example:

1. User chooses Station Block C4.
2. Dwell automatically becomes 45 seconds.
3. User changes it to 60 seconds.
4. It should remain 60 seconds.

If the user then changes the destination to another block, the dwell time can reset to the appropriate default for the newly selected block.

Validate the dwell value so that negative dwell times cannot be entered.

## Active Movement Plan

Also display the dwell time associated with each applicable destination/stop in the Active Movement Plan.

The dispatcher must be able to edit the dwell time of a future/current movement-plan stop after the train has been dispatched.

This should work similarly to the existing functionality for modifying:
- destination
- arrival time

When the dwell time changes, recalculate any timing information that depends on it.

Do not require the train to be redispatched.

## Timing semantics

Treat **Arrival Time** and **Dwell Time** as separate concepts.

For a movement-plan stop:

```text
Arrival Time = time the train reaches the destination block

Departure Time = Arrival Time + Dwell Time
```

For example:

```text
Arrival:   10:05:00
Dwell:     45 sec
Departure: 10:05:45
```

The dwell time should NOT change the calculated arrival time at that same destination.

Instead, it delays when the train begins the next movement.

Therefore, when determining the available travel time for the next movement:

```text
NextLegStartTime = PreviousArrivalTime + PreviousDwellTime
```

Then suggested speed for the next leg should be calculated using the time between:

```text
Previous departure time
        ↓
Next destination arrival time
```

rather than simply:

```text
Previous arrival time
        ↓
Next destination arrival time
```

This is important because dwell time reduces the amount of actual travel time available between scheduled stops.

Example:

```text
Destination A arrival: 10:00:00
Destination A dwell:   45 sec

Destination B arrival: 10:05:00
```

The train only has:

```text
10:00:45 → 10:05:00
```

or **4 minutes 15 seconds** of travel time.

The suggested speed calculation for the A → B movement must use that time interval.

## Recalculation

When the dispatcher modifies any of the following in the Active Movement Plan:

- destination
- arrival time
- dwell time

recalculate all dependent timing/suggested-speed information as necessary.

A dwell-time change at one stop may affect the suggested speed of the movement immediately following that stop.

If the existing Active Movement Plan already has a centralized recalculation method for destination/arrival changes, extend that existing mechanism rather than creating duplicate logic.

Authority should continue to be calculated using the existing routing/authority logic.

Only modify authority if the destination/path itself changes.

Changing dwell time alone should generally affect timing/suggested speed, not the route or authority.

## Runtime train behavior

When a train actually reaches a movement-plan destination whose dwell time is greater than zero, the CTC's state/timing representation should treat the train as dwelling at that destination for the configured period before proceeding to the next movement.

At minimum, the Active Movement Plan should accurately represent:

```text
Arrived → Dwelling → Ready/Proceeding to next destination
```

using whatever states currently make sense in the CTC architecture.

Do not create an unnecessary real-time simulation system if one does not already exist.

Fit the dwell behavior into the existing train/movement-plan state machine.

## Station behavior

```text

Regular destination → default 0-second dwell
```

The value must still be editable for either type.

If the current route-generation implementation explicitly creates movement-plan entries for station blocks that the train encounters along its route, apply the same 45-second default to those station stops.

Do not create duplicate stops if a station block is already represented as the destination of an existing movement-plan entry.

## Important architectural requirement

Please treat dwell time as part of the **movement/schedule timing model**, not merely a UI field.

The intended relationship should conceptually be:

```text
             ARRIVE
                ↓
Destination Block
                ↓
        Dwell for N seconds
                ↓
             DEPART
                ↓
       Travel to next stop
                ↓
             ARRIVE
```

Thus:

```text
Departure[n] = Arrival[n] + Dwell[n]

AvailableTravelTime[n → n+1]
    = Arrival[n+1] - Departure[n]
```

and the suggested speed for the next movement should use that available travel time.
