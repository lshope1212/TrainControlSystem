# Claude Code Task: Eliminate False Zero-Authority Gaps During Train Block Transitions

## Project

Repository: https://github.com/lshope1212/TrainControlSystem

Branch: `Luke_CTC` or the current integration development branch.

This task concerns safety-critical movement-authority handoffs between CTC, Track Controller, Track Model, Train Model, and Train Controller.

**Primary objective:** Prevent an otherwise valid, continuously moving train from receiving a temporary zero-authority command merely because its movement request is being transferred from one block to the next.

**Equally important objective:** Preserve immediate emergency-brake response to a genuine loss or revocation of movement authority.

Do not implement a grace period that suppresses actual zero authority.

## 1. Existing architecture and problem

The current implementation uses `MovementSuggestionMessage`, which contains:

- `RequestId`
- `TrainId`
- `TargetBlockId`
- `EntryBlockId`
- `PathBlockIds`
- `SuggestedSpeedMetersPerSecond`
- `SuggestedAuthorityMeters`
- `AuthorityReference = TargetBlockEntry`
- `IsActive`

Relevant files include:

- `src/CTC/CTC.Core/Dispatching/MovementRequestCoordinator.cs`
- `src/CTC/CTC.Core/Dispatching/MovementRequestPlan.cs`
- `src/CTC/CTC.Core/Tracking/TrainLocationTracker.cs`
- `src/CTC/CTC.Core/Services/CTCService.cs`
- `src/CTC/CTC.Wpf/Services/CtcNamedPipeReceiver.cs`
- `src/TrackController/TrackController.Core/Services/TrackControllerService.cs`
- `src/TrackController/TrackController.Core/Services/TrackControllerService.Requests.cs`
- `src/TrackController/TrackController.Core/Services/TrackControllerService.Evaluation.cs`
- `src/TrackController/TrackController.Core/Services/TrackControllerService.VitalPlc.cs`
- `src/TrackController/TrackController.Wpf/Services/WaysidePipeHost.cs`
- `src/TrackModel/TrackModel.Core/Services/TrackService.cs`
- `src/TrainController/TrainController.Core/Control/AuthorityTracker.cs`
- `src/TrainController/TrainController.Core/Safety/AuthorityProtection.cs`

Currently, when a train moves from Block A to Block B:

1. Track Model reports the occupancy change.
2. Track Controller retires the movement request for A when A becomes clear.
3. CTC infers that the train entered B.
4. CTC sends cancellation for A.
5. CTC sends a new movement request targeting B.
6. Track Controller evaluates it.
7. Track Controller publishes the new authority to Track Model.

During this sequence, the new block may temporarily report zero authority.

This is problematic because the Train Controller's authority protection treats insufficient authority while moving as an emergency-brake condition.

The current handoff is therefore not suitable for uninterrupted train movement.

### Important constraints

Simply reversing the cancellation and creation operations is insufficient.

Track Controller currently rejects overlapping active routes, and a movement request targeting an unoccupied block cannot yet receive positive authorization.

Also, Track Model stores commanded authority by block.

You must investigate and address these behaviors rather than only changing message ordering.

## 2. Required behavior

Implement a coordinated authority handoff that allows a valid train to move between blocks without an artificial zero-authority interruption.

Use a **prepare → transfer → retire** approach, or an equally safe and demonstrably correct solution that fits the existing architecture.

### Phase A: Prepare the successor

While the train occupies Block A and has valid authority extending into Block B:

- CTC prepares a successor movement request for B.
- The successor uses a new request ID.
- It identifies A as the entry block.
- It includes the remaining authorized route.
- It retains the same absolute authority endpoint as the original movement.
- Track Controller validates the proposed route, ownership, topology, and safety requirements.
- Track Controller records the successor as staged/pending.

The staged request must not independently grant a second overlapping movement authority.

It must not interfere with the existing active request or cause the conflict detector to withdraw valid authority.

A successful preparation acknowledgement means only that the successor is prepared. It must never be interpreted as a grant of authority.

### Phase B: Transfer authority

When fresh Track Model occupancy feedback confirms the appropriate A-to-B transition:

- Track Controller revalidates the successor against current conditions.
- Verify the transition is consistent with the staged route and cannot ambiguously represent another train.
- Treat train IDs carried by CTC as labels, not independently verified occupancy identities.
- Confirm that no conflicting movement, unsafe equipment condition, or loss of freshness exists.
- If safe, promote the successor and retire the predecessor as one atomic Track Controller state transition.
- Never grant two conflicting authorities simultaneously.
- Publish the resulting authority using the successor request ID.

The predecessor must not need to be cancelled first in a separate network operation.

If the handoff is invalid, the controller must withhold authority rather than force a successful transfer.

### Phase C: Retire the predecessor

Once the replacement is active:

- Retire the predecessor.
- Reject late renewals of its old request ID.
- Handle late or duplicate cancellation messages idempotently.
- Prevent replayed messages from reactivating retired authority.
- Record the transition clearly for CTC diagnostics.

The entire transfer must preserve the existing independent safety checks and PLC restrictions.

## 3. Preserve the fixed authority endpoint

The existing implementation intentionally defines movement authority relative to the entry of the current target block.

Maintain this behavior.

Example, using hypothetical 50 m blocks:

Initial request:

- Target: A
- Authority: 300 m
- Fixed endpoint: 300 m from A's entry

After advancing into B:

- Target: B
- Entry: A
- Authority: 250 m
- Fixed endpoint: unchanged

Do not restart the original 300 m allowance when the train enters B.

Do not extend authority simply because a request was transferred, renewed, resent, or acknowledged.

Preserve existing speed restrictions and any reductions imposed by Track Controller.

A dispatcher re-plan may establish a new endpoint, but a routine block transition must not.

## 4. Eliminate the downstream false-zero gap

This requirement is essential.

A correct CTC/Track Controller handoff is insufficient if Track Model or Train Model still exposes temporary zero authority during the transition.

Investigate the complete data flow:

Track Controller → Track Model → Train Model → Train Controller.

Track Model currently receives `TrackModelCommandBatchMessage`, while individual `TrackModelTrainEnvironmentMessage` values contain block-specific authority.

Determine how the train receives its actual movement authority when its occupied block changes.

Implement the appropriate synchronization and contract changes so that:

- Authority belongs to a validated movement and its fixed endpoint, rather than being treated as an unrelated allowance restarted at each block.
- A successful, safe block handoff preserves the train's valid authority.
- No intermediate default-zero block value is incorrectly interpreted as an authoritative zero command for that train.
- The receiving module can distinguish an expected handoff from an actual revocation.
- Messages are correlated with train identity, movement/request identity, and ordering information as needed.
- Replayed or out-of-order updates cannot restore withdrawn authority.
- A train never receives more authority than the Track Controller has actually granted.

Consider an explicit train-scoped authority state or grant/revocation contract if the existing per-block commands cannot safely represent this distinction.

Keep the existing named-pipe architecture and shared contracts.

Do not introduce an unbounded authority cache or simply continue using the last nonzero value regardless of safety state.

Where atomic batch application is required, make the state transition atomic from the consuming train's perspective.

Where the current Train Model/Train Controller live integration is incomplete, identify and implement the necessary compatible interfaces. Do not claim end-to-end continuity is achieved without verifying those consumers.

## 5. Genuine zero authority must remain safety-critical

**THIS IS THE MOST IMPORTANT SAFETY REQUIREMENT.**

The change must distinguish between:

**Case A — Normal, valid handoff**

A train travels from A into B with a valid, still-protected movement endpoint.

Expected result: Authority remains continuous. No emergency brake is caused merely by request replacement.

**Case B — Actual authority revocation**

Examples:

- Track Controller determines movement is unsafe.
- The route becomes occupied or blocked in a way that requires immediate withdrawal.
- Required equipment or feedback becomes unsafe.
- A genuine zero-authority command is issued.
- The current grant is revoked or expires.
- The handoff fails safety validation.

Expected result: Authority is withdrawn or restricted according to the actual wayside decision. Any resulting emergency-brake condition must be handled immediately by the Train Controller on receiving that authoritative safety event.

### Non-negotiable rules

DO NOT:

- Add a fixed delay before applying zero authority.
- Ignore zero authority for a few simulation ticks.
- Filter zero authority based only on how recently the train changed blocks.
- Preserve authority after an explicit revocation.
- Override PLC decisions.
- Relax occupancy or route conflict protection.
- Assume missing feedback means the previous authorization is still valid.
- Turn an invalid successor request into an automatic grant.
- Modify emergency-brake stopping-distance thresholds merely to hide this issue.

Investigate how explicit authority revocation reaches Train Model and Train Controller.

If the current 500 ms wayside publication interval delays urgent revocations, provide an event-driven safety update path that does not wait for the next routine periodic batch. Preserve ordered delivery and safe behavior on communication failure.

Real network and control scheduling cannot guarantee literally zero physical latency, but the software must introduce no intentional grace period or debounce before acting on a genuine revocation.

Review `AuthorityTracker` and `AuthorityProtection` to ensure an explicit authoritative zero is not accidentally ignored during an invalid track-signal condition.

Preserve the existing Train Controller safety algorithms wherever possible.

## 6. Request lifecycle and communication handling

Update CTC's movement request coordinator to distinguish:

- Active request
- Staged successor
- Successful transfer
- Rejected or expired successor
- Explicit revocation
- Retired predecessor

Requirements:

- Prepare the next request proactively when a safe successor block exists.
- Keep staged and active requests separate in the Track Controller.
- Ensure staged requests do not produce conflicting active grants.
- Renew or expire staged requests safely.
- Use request IDs to correlate all acknowledgements and transitions.
- Avoid duplicate successor creation from repeated occupancy messages.
- Handle CTC reconnects without resurrecting stale grants.
- Handle delayed and out-of-order messages.
- If CTC stops, existing safety watchdogs must remain effective.
- If a train changes route, cancel invalid staged successors and prepare the correct replacement.
- If a train reaches its final destination, correctly terminate its movement authorization.
- If no successor is valid, fail safely rather than masking zero authority.

CTC must continue addressing blocks through their unique block IDs.

Do not introduce knowledge of Track Controller territory ownership into CTC.Core.

Preserve compatibility with the existing three-line deployment.

## 7. Testing requirements

Add comprehensive unit and integration tests.

Use the production CTC, Track Controller, Track Model, and relevant Train Controller authority handling wherever possible.

### Test A — Normal transition without authority interruption

1. Place a train in Block A.
2. Grant authority extending through B and several blocks beyond.
3. Prepare the successor for B.
4. Simulate the actual A-to-B occupancy transition.
5. Verify that the successor becomes active and the predecessor is retired.
6. Observe the authoritative train-level outputs throughout the transition.

Assert that no artificial zero authority is delivered to the moving train.

Test both transitions where A and B occupancy changes arrive together and where observations arrive in separate messages.

### Test B — Genuine emergency revocation

Repeat with the train moving.

Introduce a genuine safety condition requiring withdrawal of all movement authority:

- Before the block transition.
- During successor preparation.
- During the transfer.
- Immediately after transfer.

Verify that the authoritative zero/revocation reaches the Train Controller without a grace delay and triggers the existing emergency-brake protection when required.

An already prepared successor must not override the revocation.

### Test C — Fixed endpoint

Verify that moving from A to B decreases authority measured from the target entry by the appropriate block length.

Confirm that the original endpoint never extends accidentally.

### Test D — Unsafe or missing successor

Test:

- Missing staged request.
- Rejected successor.
- Occupied/conflicting next block.
- Stale Track Model feedback.
- Wrong direction of travel.
- Switch misalignment.
- Invalid signal/crossing protection.
- CTC disconnection.
- Lost acknowledgement.
- Unavailable Train Model.
- Request watchdog expiration.

Verify safe withdrawal rather than silently preserving invalid authority.

### Test E — Repeated and out-of-order updates

Ensure stale messages cannot:

- Reinstate the old request.
- Reactivate withdrawn authority.
- Duplicate a handoff.
- Cause two overlapping positive grants.
- Extend the authority endpoint.

### Test F — Multiple trains and lines

Verify independent handoffs for trains on Blue, Red, and Green.

Test two trains near one another, with conflicting or ambiguous occupancy.

Do not permit train identity to be guessed merely to complete a handoff.

### Test G — End-to-end Train Controller behavior

For a moving train with a valid, continuing movement grant, verify that the Train Controller does not engage emergency braking because of a temporary request-ID replacement.

Then issue a genuine zero-authority command and verify that the Train Controller's existing safety protection engages at the next applicable control evaluation, without a handoff grace period.

Run regression tests covering existing CTC movement requests, PLC safety, occupancy, and maintenance handling.

## 9. Implementation process

First, trace the complete existing authority lifecycle and identify every place where zero authority can appear during a normal block transition.

Then implement the smallest coherent solution that achieves all the required safety properties.

A partial fix that changes only CTC message ordering is not sufficient.

If the proposed staged-handoff design conflicts with existing safety requirements, choose a better design and explain the difference.

Preserve existing tested behavior and update tests to match the new protocol.

Proceed with implementation. Do not stop after writing a design proposal.

Run the applicable builds and automated tests.

Do not weaken tests or safety checks merely to make the suite pass.

### Definition of done

The task is complete only when:

- A moving train can transition between blocks without receiving a false zero caused by request replacement.
- Authority never exceeds the wayside-approved fixed movement endpoint.
- No conflicting positive movement authorities are created.
- A genuine zero-authority decision is never delayed or suppressed to facilitate a handoff.
- Stale feedback, missing requests, and communication failures remain fail-safe.
- Existing CTC functionality works across Blue, Red, and Green.
- Integration tests demonstrate both uninterrupted valid movement and immediate safety response to actual revocation.

**Safety behavior takes precedence over uninterrupted movement. If continuity cannot be achieved safely in a scenario, the train must be allowed to brake.**
