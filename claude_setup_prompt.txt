## 1. Change "Current Block" to "Last Known Block" for dispatched trains

Currently, when a train is dispatched, `DispatchedTrainState.CurrentBlockId` is initialized to the train's scheduled starting block.

For example, a train starting at A1 will continue to display:

`Current Block: A1`

even after it has theoretically moved.

This is misleading during our current isolated-module implementation.

The Track Controller reports block occupancy using `BlockStatusMessage`, but this message intentionally does NOT identify which train is occupying a block. Therefore CTC cannot reliably infer that a particular dispatched train has moved from one block to another.

We are intentionally leaving actual train-location tracking for later system integration.

### Desired behavior

Replace the concept exposed to the UI as "Current Block" with:

`Last Known Block`

When a train is initially dispatched, its last known block should still be initialized to its scheduled start block because that is the last location CTC can authoritatively associate with the train.

For now it should remain at that value indefinitely.

Later, once the integrated system provides a reliable train-position message containing a train identity and location, this field can be updated.

### Implementation requirements

Please inspect:

- `CTC.Core/Models/DispatchedTrainState.cs`
- `CTC.Core/Services/CTCService.cs`
- `CTC.Wpf/ViewModels/DispatchedTrainViewModel.cs`
- the dispatched-train DataGrid/table in `CTC.Wpf/MainWindow.xaml`
- any tests or other references to `CurrentBlockId`

Make the naming consistent through the relevant CTC code.

I would prefer the core model property to become something like:

```csharp
public string LastKnownBlockId { get; set; } = string.Empty;
```

instead of retaining the misleading `CurrentBlockId` name.

Update the dispatch logic so:

```csharp
dispatched.LastKnownBlockId = scheduledTrain.StartBlockId;
```

Update comments/XML documentation to clearly explain:

- this is the last location CTC can authoritatively associate with the train;
- initially it is the scheduled route start block;
- Track Controller occupancy alone cannot update it because `BlockStatusMessage` contains no `TrainId`;
- true train-position updates are deferred until module integration.

Update the WPF ViewModel/property names as appropriate and change the dispatched-trains UI column header from:

`Current Block`

to:

`Last Known Block`

Do NOT implement any logic that guesses a train's location based on block occupancy transitions.

Do NOT modify `BlockStatusMessage` to add a train ID.

Do NOT add fake movement simulation to CTC.

The purpose of this change is simply to accurately represent what CTC actually knows.

## 2. Add a "Clear Template" button to the Schedule Builder

Currently, once a schedule template has been generated in the Schedule Builder, there is no obvious way for the dispatcher to completely clear it and return to the initial empty state without restarting/changing state elsewhere.

`ScheduleBuilderViewModel` already has a private `ClearTemplate()` helper that clears:

- `_template`
- `Rows`
- `TrainColumns`

I want this functionality exposed to the user.

### Desired behavior

Add a button to the Schedule Builder UI labeled:

`Clear Template`

The button should clear the currently generated schedule template so that the schedule grid returns to its empty/pre-generated state.

It should NOT:

- clear the imported track layout;
- clear dispatched trains;
- remove an already queued schedule from CTC;
- reset system time;
- modify any other CTC state.

It should only clear the editable Schedule Builder template currently shown in the UI.

After clearing, update `StatusMessage` to something clear, such as:

`Schedule template cleared. Enter the number of trains and generate a new template.`

The user should then be able to immediately generate another template.

### MVVM implementation

Follow the existing command pattern in `ScheduleBuilderViewModel`.

Add something along the lines of:

```csharp
public ICommand ClearTemplateCommand { get; }
```

Initialize it alongside `GenerateTemplateCommand`, `QueueScheduleCommand`, and `UploadScheduleCommand`.

The command should call a small public-facing/private command handler rather than putting UI logic into code-behind.

The existing `ClearTemplate()` helper can continue doing the actual collection clearing.

The command should only be enabled when a template currently exists if that fits cleanly with the existing RelayCommand implementation.

Place the button logically alongside the existing Schedule Builder controls such as Generate/Queue/Upload rather than creating a new unrelated panel.

Match the existing WPF styling.

## 3. Preserve and verify the existing occupied-start-block dispatch protection

Do NOT remove or weaken the existing dispatch safety behavior.

The current system should behave as follows:

1. Sample Blue Line layout is loaded.
2. Track Controller/TestUI sends a `BlockStatusMessage` marking A1 as occupied.
3. A schedule is built for a train whose route starts at A1.
4. The train reaches its scheduled departure time.
5. `AuthorityManager.CalculateInitialAuthorityMeters()` should return zero because the first route block is unsafe.
6. CTC must NOT send the movement suggestion/release for that train.
7. The train must remain queued.
8. The CTC UI should tell the dispatcher that dispatch failed because the starting block is occupied or closed for maintenance.
9. The train should remain eligible to retry on a future system-time update after the block becomes clear.

The existing implementation appears to already provide this behavior through `AuthorityManager`, `DispatchTrainAsync`, `DispatchFailed`, and `MainWindowViewModel`.

Please verify it remains intact after your changes.

If there is already an appropriate automated test for this case, preserve it.

If there is no test, add a focused unit test covering at least:

```text
Start block occupied
→ initial authority = 0
→ train is not moved into DispatchedTrains
→ train remains in DispatchQueue
```

If practical within the existing test architecture, also verify that the dispatch-failure event contains an informative message mentioning the occupied start block.

Do not change the behavior to reject the schedule when it is initially built. Occupancy is live state and may change between schedule creation and departure, so the safety check belongs at dispatch time as it currently does.
