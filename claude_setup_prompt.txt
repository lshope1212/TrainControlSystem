PART 2 — USE CASE DIAGRAM RULES
============================================================

The use case diagram is intended to be a graphical table of contents for the CTC use case set.

It should contain exactly ONE primary actor:

    Dispatcher

Do NOT add the following as actors to the use case diagram:

- Track Controller
- Track Model
- Train Controller
- System Clock
- Test UI
- CTC itself
- message transport

PART 4 — SEQUENCE DIAGRAM NOTATION / STYLE
============================================================

Follow standard UML sequence diagram conventions and the style used in our System Modelling lecture:

- Participants/objects are listed horizontally across the top.
- Each participant has a vertical lifeline.
- Time proceeds downward.
- Method calls/messages are horizontal annotated arrows.
- Activation bars should be shown where useful.
- Return messages are optional; show them only when the returned value is important to understanding the scenario.
- Prefer participant labels of the form:

      objectName : ClassName

  or:

      :ClassName

  Examples:

      dispatcher : Dispatcher
      mainVM : MainWindowViewModel
      scheduleVM : ScheduleBuilderViewModel
      ctc : CTCService
      routeManager : RouteManager

- The leftmost participant should normally be the Dispatcher actor for these user-initiated use cases.
- The UI/ViewModel boundary should be visible when it materially explains how the action is initiated.
- Do not show every framework implementation detail of ICommand, WPF binding internals, async state machines, property notification machinery, Task internals, etc.
- It is acceptable to label the first message from Dispatcher to a ViewModel as the corresponding UI action / command, e.g.:

      click "Queue Schedule"
      QueueScheduleCommand.Execute()

  Then transition to actual application methods.

- Do NOT draw a sequence diagram like an activity diagram.
- Do NOT attempt to represent every line of code.
- Show the collaborations between the important objects.

Our lecture emphasizes that a sequence diagram captures a SINGLE SCENARIO/use-case instance. Therefore make the normal/main-success path the primary sequence.

Use UML combined fragments sparingly:

    alt
    opt
    loop

Only use them when a branch is important to understanding the use case.

Do NOT expand every validation `if` statement into a giant conditional tree.

For example, a single concise `alt` block such as:

    [validation succeeds]
    [validation fails]

may be appropriate when validation is architecturally important.

If detailed algorithms, loops, or conditional logic become complicated, summarize them in a note or one method call rather than exploding the diagram. The point is to show object collaboration.
