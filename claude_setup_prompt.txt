We need to make one relatively small change to the CTC module for this iteration.

Please inspect the current CTC implementation before making changes, especially:

- `src/CTC/CTC.Wpf/MainWindow.xaml`
- `src/CTC/CTC.Wpf/ViewModels/MainWindowViewModel.cs`
- `src/CTC/CTC.Wpf/ViewModels/BlockViewModel.cs`
- Any existing commands associated with closing/reopening blocks and toggling switches

## Goal

The **Block Controls** section of the CTC window should only be usable when the CTC operator has explicitly enabled **Maintenance Mode**.

This is an operator/UI mode for the CTC application. It is **not the same thing as the existing per-block `MaintenanceState` / requested maintenance state**.

Do not modify the meaning of `MaintenanceState`, do not mark every block as being in maintenance, and do not send any message to another module simply because Maintenance Mode was turned on or off.

---

## Required behavior

### 1. Add a Maintenance Mode toggle to the Block Controls section

In the existing **Block Controls** panel in `MainWindow.xaml`, add a button near the top of the section that toggles Maintenance Mode.

The UI should make the current state obvious. For example, the button can display:

- `Maintenance Mode: OFF`
- `Maintenance Mode: ON`

A small status label or reasonable visual difference between ON/OFF is also fine, but keep it consistent with the existing CTC UI styling. Do not redesign the panel.

Maintenance Mode must default to **OFF** when the CTC application starts.

The Maintenance Mode toggle itself must ALWAYS remain enabled so the operator can enter or leave Maintenance Mode.

---

### 2. Disable all actual block-control actions while Maintenance Mode is OFF

When Maintenance Mode is OFF, the following existing Block Controls must be disabled:

- Close Block
- Reopen Block
- Toggle Switch

The selected-block information above the Block Controls section should remain usable/readable. Only the controls that modify track/block state should be restricted.

A clean way to handle this in XAML is to leave the Maintenance Mode toggle outside of a child container and bind that child container's `IsEnabled` to `IsMaintenanceMode`.

For example, conceptually:

```text
Block Controls
    [ Maintenance Mode: OFF ]     <-- always usable

    Child controls container      <-- IsEnabled = IsMaintenanceMode
        [ Close Block ]
        [ Reopen Block ]

        Track Switch
        [ Toggle Switch ]
```

Do not blindly use this exact XAML; fit it into the existing layout.

---

### 3. Preserve the existing Toggle Switch rule

The existing behavior where **Toggle Switch is only available when the selected block actually has a switch must remain**.

Currently the XAML has logic equivalent to:

```xml
IsEnabled="{Binding SelectedBlock.HasSwitch}"
```

The resulting behavior must be:

| Maintenance Mode | Selected block has switch | Toggle Switch |
|---|---|---|
| OFF | No | Disabled |
| OFF | Yes | Disabled |
| ON | No | Disabled |
| ON | Yes | Enabled |

Do not remove the `HasSwitch` protection just to add Maintenance Mode.

If using an `IsEnabled` parent container, WPF's inherited disabling should naturally provide both restrictions: the parent requires Maintenance Mode, while the Toggle Switch retains its own `SelectedBlock.HasSwitch` condition.

If the command already has a `CanExecute`, also preserve that logic.

---

## ViewModel changes

Implement this using the existing MVVM architecture.

In `MainWindowViewModel`, add something equivalent to:

```csharp
private bool _isMaintenanceMode;

public bool IsMaintenanceMode
{
    get => _isMaintenanceMode;
    private set
    {
        if (SetProperty(ref _isMaintenanceMode, value))
        {
            OnPropertyChanged(nameof(MaintenanceModeButtonText));

            // If necessary for the existing command implementation:
            CommandManager.InvalidateRequerySuggested();
        }
    }
}

public string MaintenanceModeButtonText =>
    IsMaintenanceMode
        ? "Maintenance Mode: ON"
        : "Maintenance Mode: OFF";
```

Add a command such as:

```csharp
public ICommand ToggleMaintenanceModeCommand { get; }
```

and initialize it in the constructor using the project's existing `RelayCommand` pattern.

The command should simply toggle:

```csharp
IsMaintenanceMode = !IsMaintenanceMode;
```

Use the actual `RelayCommand` constructor/signature already used by this project rather than assuming the exact syntax above.

---

## Command-level protection

Do not rely exclusively on graying out the XAML.

Where practical, make the existing block-control commands' `CanExecute` logic also require Maintenance Mode.

For example, the Close Block rule should become conceptually:

```csharp
IsMaintenanceMode
&& SelectedBlock is not null
&& SelectedBlock.RequestedMaintenanceState != MaintenanceState.Closed
```

Likewise:

- Reopen Block should require Maintenance Mode plus whatever existing conditions it already uses.
- Toggle Switch should require Maintenance Mode plus `SelectedBlock.HasSwitch` plus any existing conditions.

**Preserve all existing command-specific rules.** Maintenance Mode is an additional requirement, not a replacement for them.

If some of these commands are currently controlled entirely through XAML rather than `CanExecute`, do not unnecessarily rewrite the architecture. Just make sure they cannot execute while Maintenance Mode is OFF.

---

## Important distinction

There are now two different concepts:

### CTC Maintenance Mode
A local operator mode controlling whether the dispatcher is allowed to use the Block Controls UI.

```text
IsMaintenanceMode = true / false
```

### Block maintenance state
The existing state/request associated with an individual track block:

```text
MaintenanceState.Open
MaintenanceState.Closed
```

These must remain separate.

Turning CTC Maintenance Mode ON must NOT:

- close any block,
- reopen any block,
- change a block's `RequestedMaintenanceState`,
- send `MaintenanceRequestMessage`,
- send `SwitchPositionRequestMessage`,
- or otherwise communicate with another module.

It simply unlocks the existing controls.

## Expected behavior / acceptance test

After implementation, verify the following manually:

1. Start the CTC application.
2. Maintenance Mode initially displays **OFF**.
3. Close Block, Reopen Block, and Toggle Switch are disabled.
4. Select a block that contains a switch.
5. Toggle Switch must still be disabled because Maintenance Mode is OFF.
6. Press the Maintenance Mode button.
7. It changes to **ON**.
8. Close/Reopen become available according to their existing block-state rules.
9. With a block containing a switch selected, Toggle Switch becomes available.
10. Select a block without a switch.
11. Toggle Switch becomes disabled even though Maintenance Mode remains ON.
12. Select a block with a switch again.
13. Toggle Switch becomes enabled again.
14. Turn Maintenance Mode OFF.
15. All Block Controls immediately become disabled again.
16. The Maintenance Mode button itself remains enabled throughout.
17. Toggling Maintenance Mode alone does not modify CTC Core state or send any outgoing messages.

## Scope

Keep this change small.

Do NOT:

- redesign the CTC window,
- create a new service just for Maintenance Mode,
- add a new shared contract/message,
- modify Track Controller behavior,
- change the meaning of the existing `MaintenanceState`,
- change block closing/reopening logic beyond adding the Maintenance Mode guard,
- remove the existing `HasSwitch` restriction,
- or refactor unrelated CTC functionality.

Follow the existing MVVM conventions and naming/style of the project.

After implementing the change:

1. Build the affected CTC projects/solution.
2. Fix any binding or compilation errors caused by the change.
3. Briefly summarize which files were modified and what changed in each.
