I want you to refactor the CTC/TestUI architecture in the existing TrainControlSystem repository.

IMPORTANT: Before changing anything, inspect the CURRENT repository and current branch. Do not blindly recreate classes or overwrite working functionality. Reuse existing contracts, services, view models, commands, and named-pipe infrastructure where appropriate.

The current CTC/TestUI implementation was built around an architectural assumption that needs to change.

======================================================================
CURRENT PROBLEM
======================================================================

Right now:

- `CTC.Wpf` creates its own `CTCService`.
- `CTC.TestUI.Wpf` creates a completely separate `CTCService`.
- Both projects reference `CTC.Core`.
- The TestUI directly calls methods such as:
  - `ApplyTrackLayout(...)`
  - `ApplyBlockStatus(...)`
  - `SetSystemTime(...)`
  - `CloseBlockAsync(...)`
- The TestUI uses `RecordingMessageSender` to capture messages generated by its own private CTCService.

This means the TestUI is currently a standalone frontend/test harness for CTC.Core.

Conceptually:

    CTC.Wpf.exe
        |
        +--> CTCService instance #1
                |
                +--> CtcSystemState #1

    CTC.TestUI.Wpf.exe
        |
        +--> CTCService instance #2
                |
                +--> CtcSystemState #2

That is NOT the architecture we now want.

Because these are separate executable processes, those CTCService instances do not share memory.

For example, changing Block G12 to Occupied in the TestUI currently changes only the TestUI's private CTC state. It cannot update the actual running CTC.Wpf window.

======================================================================
NEW ARCHITECTURAL INTENT
======================================================================

The TestUI should NOT be another frontend to CTC.Core.

Instead:

    THE TEST UI SHOULD PRETEND TO BE THE EXTERNAL MODULES
    THAT ARE NOT YET AVAILABLE.

It should interact with the REAL running CTC module through the same process boundary that the real modules will eventually use.

The intended development architecture is:

                        CTC MODULE

                  +------------------+
                  |     CTC.Wpf      |
                  |                  |
    inbound IPC ->| receiver         |
                  |      |           |
                  |      v           |
                  |   CTCService     |
                  |      |           |
                  |      v           |
                  | CtcSystemState   |
                  |      |           |
                  |      v           |
                  | Real CTC UI      |
                  |                  |
                  | outgoing sender -|----> outbound IPC
                  +------------------+

                           ^        |
                           |        v

                  +------------------+
                  |   CTC.TestUI     |
                  |                  |
                  | Simulates:       |
                  | Track Controller |
                  | Track Model      |
                  | shared inputs    |
                  |                  |
                  | Captures CTC     |
                  | outgoing msgs    |
                  +------------------+

The TestUI and normal CTC UI should be able to RUN AT THE SAME TIME.

======================================================================

======================================================================

The important property of this architecture is:

    THE TEST UI MUST BE DISPOSABLE.

During development:

    TestUI
       |
       | BlockStatusMessage

       | MaintenanceRequestMessage

    TestUI

Later:

    Track Controller
       |

       v
      CTC
       |

       v
    Track Controller

CTC itself should not need architectural changes when the TestUI is replaced by the real external module.

The TestUI must use the same shared contracts and communication boundary that the real modules will eventually use.

======================================================================
SHARED TRANSPORT PROTOCOL
======================================================================

The existing `NamedPipeMessageSender` already uses newline-delimited JSON and an
envelope similar to:

    {
        "messageType": "MaintenanceRequestMessage",
        "payload": {
            "blockId": "G12",
            "requestedState": "Closed"
        }
    }

Preserve this concept.

Do not create a different protocol for TestUI -> CTC.

Both directions should use the same basic envelope convention:

    messageType
    payload

Enums should serialize as readable strings.

Use `System.Text.Json`.

Continue using one complete JSON envelope per line / per connection for now.

A persistent connection is NOT required.

One named-pipe connection per sent message is acceptable.

======================================================================
SHARED COMMUNICATION UTILITIES
======================================================================

Avoid having several incompatible private implementations of the envelope format.

Where cleanly appropriate, move GENERIC transport helpers into
`TrainControl.Common`.

For example, something conceptually like:

    TrainControl.Common
        Communication/
            MessageEnvelope.cs
            MessageSerializer.cs
            NamedPipeNames.cs

This is only a suggested organization. Adapt to the existing repository structure
if a better location already exists.

Possible constants:

    CTC pipe:
        "TrainControl.CTC"

    Track Controller pipe:
        "TrainControl.TrackController"

Do NOT put those constants in CTC.Core.

`NamedPipeNames` should contain only communication endpoint names and no business
logic.

The existing `NamedPipeMessageSender` should reuse the shared envelope serializer
rather than maintaining its own incompatible private format if doing so is clean.

Do not unnecessarily build a large messaging framework.

Keep this small.

======================================================================
PART 1 — CREATE THE CTC INBOUND RECEIVER
======================================================================

CTC.Wpf currently knows how to SEND outgoing messages through
`NamedPipeMessageSender`.

It now also needs to RECEIVE incoming messages.

Add a service in CTC.Wpf with an appropriate name such as:

    CtcNamedPipeReceiver

or:

    NamedPipeMessageReceiver

Suggested location:

    src/CTC/CTC.Wpf/Services/

It should listen on:

    TrainControl.CTC

using:

    NamedPipeServerStream

Use asynchronous named-pipe operations.

The receiver should:

1. Start when CTC.Wpf starts.

2. Continuously wait for incoming connections until the application shuts down.

3. Read one newline-delimited JSON envelope.

4. Inspect `messageType`.

5. Deserialize the payload into the corresponding REAL shared contract type.

6. Route the message into the SINGLE actual CTCService instance used by CTC.Wpf.

7. Dispose the connection.

8. Go back to waiting for the next connection.

9. Handle malformed messages gracefully.

10. Handle unknown message types gracefully.

11. Never terminate the receiver loop because one client sent a bad message.

======================================================================
SUPPORTED INBOUND MESSAGE ROUTING
======================================================================

At minimum route the contracts CTC already understands.

For example:

    BlockStatusMessage
        -> ICTCService.ApplyBlockStatus(...)

    TrainAuthorizationStatusMessage
        -> ICTCService.ApplyTrainAuthorization(...)

    TicketSalesMessage
        -> ICTCService.ApplyTicketSales(...)

Do not duplicate CTC business logic inside the receiver.

The receiver's job is ONLY:

    JSON
      ->
    shared contract
      ->
    correct ICTCService method

======================================================================

    IMessageSender sender = new NamedPipeMessageSender();
    ICTCService ctcService = new CTCService(sender);

Refactor startup so dependency construction happens once.

Prefer moving composition to `App.xaml.cs`.

A reasonable structure is:

    App.OnStartup(...)
        |
        +--> create NamedPipeMessageSender
        |
        +--> create ONE CTCService
        |
        +--> create MainWindowViewModel using that service
        |
        +--> create MainWindow using that VM
        |
        +--> create CTC inbound receiver using SAME service
        |
        +--> start receiver
        |
        +--> show MainWindow

If necessary, remove:

    StartupUri="MainWindow.xaml"

Do not use a global service locator.

Do not use static CTCService state.

Use normal explicit composition.

======================================================================
APPLICATION SHUTDOWN
======================================================================

The named-pipe receive loop must stop cleanly when CTC exits.

Use a `CancellationTokenSource` owned by the CTC application/composition root.

Cancel it during application shutdown.

Do not leave an uncontrolled background thread or infinite task.

======================================================================
THREADING / WPF SAFETY
======================================================================

Named-pipe receive operations will run asynchronously.

CTC state ultimately backs WPF data.

Do not mutate UI-observed state unsafely from arbitrary background threads.

Since the inbound receiver lives in CTC.Wpf, it is acceptable for the receiver or
a small WPF-side coordinator to marshal the final call into the WPF Dispatcher.

For example conceptually:

    await Application.Current.Dispatcher.InvokeAsync(
        () => _ctc.ApplyBlockStatus(message));

or an equivalent clean design.

Do NOT put Dispatcher code into CTC.Core.
