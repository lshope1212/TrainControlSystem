# Task: Extend Live CTC Integration to All Three Railway Lines

## Project context

Repository: https://github.com/lshope1212/TrainControlSystem

Working branch: `Luke_CTC` (or the current active development branch if changes have moved).

We recently completed a significant portion of the live integration between the Centralized Traffic Control (CTC), Track Controller, and Track Model modules.

The Blue Line currently supports real named-pipe communication between these modules, including:

- Automatic track layout synchronization from Track Model to CTC.
- Live block occupancy and equipment status updates through the Track Controller.
- CTC maintenance requests, acknowledgements, and confirmed block closures.
- Movement suggestions containing speed, authority, and route information.
- Track Controller evaluation of movement requests and reporting of its actual authorization.
- Stale-feedback detection and communication failure handling.
- CTC train-location inference using sequential block occupancy.

However, this functionality has only been fully integrated and demonstrated using the production Blue Line setup.

**Your task is to extend the existing functionality so the Blue, Red, and Green Lines can all operate simultaneously through the real Track Model, Track Controller, and CTC modules.**

This is an actual system integration task, not a UI demonstration or additional TestUI implementation.

Determine what is already implemented, what is Blue-specific, and what must change for multi-line operation.

**Do not rebuild working functionality unnecessarily. Extend the existing architecture.**

## 2. Support the actual Red and Green Line layouts

The course project uses three railway lines:

| Line | Blocks |
|---|---:|
| Blue | 15 |
| Red | 76 |
| Green | 150 |
| **Total** | **241** |

The CTC TestUI already contains a complete sample layout in:

`src/CTC/CTC.TestUI.Wpf/SampleData/course-vf5-layout.json`

This fixture was generated from the course's `Track Layout & Vehicle Data vF5` workbook.

However, the production Track Model currently defaults to the Blue Line, and its Excel workbook importer is Blue-specific.

### Requirements

1. Extend the production Track Model to load all three railway lines simultaneously.
2. Use the actual course topology and block properties, including section identifiers, lengths, speed limits, stations, connections, switches, signals, and crossings.
3. Reuse existing validated course data where possible instead of manually inventing layouts.
4. Preserve existing Blue Line behavior.
5. Ensure Track Model publishes one complete `TrackLayoutMessage` containing all three lines.
6. Ensure CTC automatically receives and displays all three lines without requiring `Send Sample Layout`.
7. Preserve the existing layout synchronization/reconciliation behavior.

Important: The CTC TestUI fixture is a contract-level layout, not necessarily a production Track Model file. If necessary, create a validated conversion process rather than simply deserializing it into an incompatible model.

Do not use the generic Track Controller Green Line demonstration map as a substitute for the actual course Green Line.

If any required track data is missing or ambiguous, identify the issue explicitly rather than inventing connections or properties.

## 3. Standardize block identifiers

Block IDs must be globally unique across all three lines because the existing shared messages generally identify blocks without including a separate line ID.

Requirements:

- Preserve the existing production Blue Line IDs (`1`–`15`) unless there is a compelling compatibility reason to change them.
- Give Red and Green unique, consistent identifiers, such as `RED-12` and `GREEN-12`.
- Use exactly the same IDs in Track Model, Track Controller, and CTC.
- Do not introduce implicit ID conversions inside CTC.
- Keep section and block-number metadata separate from the unique block ID.
- Validate that no duplicate block IDs exist across the entire network.

Update every related reference, including topology connections, switch configurations, protection zones, station/beacon references, and deployment files.

**Track Model must remain the authoritative source of block identities and the physical layout.**

## 4. Configure the Track Controller for all three lines

The Track Controller currently supports deployment configurations and multiple wayside territories through its runtime architecture.

Investigate how to extend this architecture to support the entire 241-block network.

### Requirements

- Support a combined configuration containing Blue, Red, and Green.
- Every production block must be owned by exactly one Track Controller territory.
- Preserve the existing ownership-routing architecture.
- Configure the appropriate topology and equipment for each line.
- Ensure the Track Controller accepts real `TrackModelBlockStateMessage` feedback for every block.
- Ensure the Track Controller can publish `BlockStatusMessage` feedback for every line.
- Maintain the existing PLC safety rules, watchdogs, and request validation.

For this integration milestone, a **single Track Controller application hosting multiple logical territories on the PC** is acceptable.

Do not require three competing processes to listen on the same named-pipe endpoint.

The design should remain compatible with future PC/Raspberry Pi deployment and multiple Track Controllers per line.

### Important architectural rule

CTC must not need to know which Track Controller owns a block.

It should continue issuing requests using the shared contracts and unique block IDs. Territory ownership and message routing belong to the Track Controller infrastructure.

Do not add territory-specific routing logic to CTC.Core.

Also, do not silently change the topology or bypass safety validation to make the combined deployment load successfully.

## 5. Live occupancy and block-status integration

This is the highest-priority functional requirement.

For every block on all three lines, the following process should work:

1. Track Model determines the block's actual state.
2. Track Model sends its state to the Track Controller.
3. Track Controller evaluates the received information.
4. Track Controller sends the corresponding block status to CTC.
5. CTC updates the correct line and block automatically.

This must work continuously without TestUI applications.

### Verify the following

- Occupancy changes update the correct block on the correct line.
- Clearing a block removes its occupied status.
- Signals, switches, crossings, failures, and maintenance status update correctly.
- An update on one line does not accidentally change another line.
- An unknown block ID is rejected rather than silently mapped.
- Stale or disconnected feedback is handled conservatively.
- Reconnecting a module restores live updates without requiring a full application restart.
- Repeated equivalent layout messages do not unnecessarily reset CTC state.

The existing functionality should behave consistently across all three lines.

## 6. Extend CTC maintenance control

The CTC dispatcher should be able to select any of the three lines and close or reopen blocks using the existing UI.

For example:

- Close a block on Blue.
- Close a block on Red.
- Close a block on Green.
- Reopen those blocks.

Each action should follow the current request/acknowledgement/confirmation design.

CTC sends the request, Track Controller acknowledges whether it was accepted, and the actual block status confirms the final state.

Preserve pending closure behavior for occupied blocks.

Do not treat successful pipe delivery as proof that a requested action was executed.

Confirm that commands on different lines do not interfere with one another.

## 7. Movement requests and authority evaluation

The existing CTC can calculate suggested speeds and authority, send complete movement requests, and interpret Track Controller authorization reports.

Extend this functionality to Red and Green wherever the current controller architecture can safely support it.

### Requirements

- CTC generates movement suggestions using the selected line's actual topology and speed limits.
- Requests contain correct block IDs and route information.
- Track Controller evaluates them against the correct territory.
- The response is correlated to the correct request.
- CTC displays actual authorization, not merely the requested authority.
- Existing request cancellation, renewal, expiration, and re-planning behavior remains intact.
- Requests are never accidentally applied to a different line.

### Cross-territory limitations

The current Track Controller can reject movement requests that cross territory boundaries.

Investigate whether this prevents otherwise valid movement requests on Red and Green.

For this milestone:

- Ensure movement requests confined to a territory work correctly.
- Preserve safe rejection for unsupported cross-territory movements.
- Do not bypass territory safety checks.
- Clearly document what would be required for future cross-territory handoff.

If a safe, straightforward solution already fits the existing architecture, you may implement it with tests. Otherwise, leave cross-territory movement as an explicitly documented limitation rather than introducing an untested redesign.

Full train physics and automatic physical train release are outside the scope of this task.

## 8. Address performance with 241 blocks

The previous Blue Line integration used frequent individual named-pipe messages.

This may become inefficient with all 241 blocks active.

Investigate:

- Track Model's one-second feedback heartbeat.
- Track Controller's 500 ms block-status publication.
- Number of named-pipe connections created.
- Whether continuous updates could delay acknowledgements or CTC UI processing.
- Whether large initial snapshots could delay layout synchronization.

Implement batching where necessary to support the complete network reliably.

The Track Controller already has some batch-input capability. Reuse existing infrastructure where appropriate.

If new batch contracts are needed, maintain compatibility with existing single-message consumers and TestUIs.

Preserve correct message ordering, request correlation, and freshness timestamps.

Do not reduce safety or freshness guarantees just to improve throughput.

## 9. Preserve existing CTC behavior

Do not make unnecessary changes to CTC's existing user interface or domain logic.

The following must continue working:

- The three-line selector.
- Territory overview/map.
- Selected block details.
- Schedule builder.
- Dispatched trains.
- Active movement plans.
- Suggested speeds and authority.
- Manual schedule modifications.
- Maintenance controls.
- Train tracking through sequential occupancy.
- Shared simulation clock controls.

Ensure the CTC territory map can handle the larger Red and Green layouts without becoming unusable.

Improve layout performance or scrolling if necessary, but avoid a major UI redesign.

Preserve the current rule that CTC never automatically assumes a command was accepted merely because it was transmitted.

## 10. Testing and verification

Add or extend automated integration tests using the actual production services, contracts, and named-pipe handlers.

Do not rely entirely on mocked services or TestUIs.

### Required tests

**Layout integration**
- All three lines load successfully.
- Expected counts are 15, 76, and 150 blocks.
- All 241 block IDs are unique.
- CTC receives all three lines automatically.
- Duplicate layout messages preserve live state.
- Restarting CTC triggers successful layout synchronization.

**Occupancy integration**
- Change a block on each line.
- Verify that the Track Controller receives the change.
- Verify that CTC receives the correct updated status.
- Verify that changes remain isolated to the correct line.
- Verify occupied-to-clear transitions.
- Verify communication failures produce conservative Unknown/stale states.

**Maintenance integration**
- Close and reopen at least one block on each line.
- Verify acknowledgements and actual confirmed status.
- Verify unsafe or invalid requests are rejected appropriately.
- Verify pending closures work correctly.

**Movement integration**
- Send a valid movement request on each line.
- Confirm the Track Controller evaluates it correctly.
- Verify the resulting authorization is reported back to CTC.
- Test unknown blocks, invalid paths, stale feedback, and territory boundaries.

**Performance**
- Confirm that all three lines can publish statuses continuously without significant backlog.
- Confirm a disconnected recipient does not block healthy modules.
- Confirm maintenance acknowledgements are not starved by bulk status updates.

Preserve existing Blue Line tests.

Run the complete solution build and all applicable tests. Report actual results, not assumptions.
