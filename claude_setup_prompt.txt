BACKGROUND / IMPORTANT ARCHITECTURAL RULE
==========================================

The CTC must NOT receive an explicit TrainId + CurrentBlock message.

There is deliberately no production I/O that tells CTC:

    Train 000 is in Block A4

This train control system is modeling the behavior of real centralized traffic
control / track-circuit systems.

The Track Controller reports anonymous block occupancy:

    Block A4 = Occupied
    Block A3 = Clear

The track circuit tells CTC that SOMETHING occupies a block, but does not
identify the train.

The CTC must determine train identity through sequential occupancy.

The principle is:

1. CTC knows where a train enters the system because CTC dispatched it.
2. CTC therefore initially associates that train with its route start block.
3. CTC knows the intended/active route for the train.
4. As occupancy progresses from one block to the next along that route, CTC
   logically moves the train identity with the occupancy.
5. A normal block-boundary transition can temporarily have BOTH blocks occupied:

       A1 = Occupied
       A2 = Occupied

   followed by:

       A1 = Clear
       A2 = Occupied

   If Train 000 was in A1 and A2 is the next block on Train 000's active route,
   the new A2 occupancy represents Train 000 progressing into A2.

6. Clearing the old block does NOT move the train. Occupancy of the next block
   moves the train identity forward.
7. CTC must never guess when the occupancy cannot be uniquely associated with
   one train.

DO NOT:
- add TrainOperatingStatusMessage
- add TrainPositionMessage
- add TrainId to BlockStatusMessage
- modify production I/O to explicitly identify the train occupying a block
- derive train identity from actual speed or some new telemetry
- use scheduled arrival time as the primary mechanism for identifying trains

The production CTC must work only from its existing knowledge:
- trains it dispatched
- their current/active routes
- track topology
- anonymous BlockStatusMessage occupancy updates

SEQUENTIAL OCCUPANCY ALGORITHM
==============================

When a block transitions into Occupied, determine whether that occupancy can
uniquely represent one dispatched train moving to its NEXT expected active-route
block.

For each dispatched train:

1. Ignore it if it is on another line.

2. Ignore it if CurrentBlockId is empty or its active route is invalid.

3. Determine its expected next block using:

       ActiveRouteBlockIds[ActiveRouteIndex + 1]

   if such a block exists.

4. The newly occupied block is a location candidate for this train ONLY if it
   exactly equals that next active-route block.

Do not skip route blocks.

Example:

    active route = A1 -> A2 -> A3
    current = A1

If A3 suddenly becomes occupied, DO NOT jump Train 000 directly from A1 to A3.

A2 must first have been established.

If exactly ONE dispatched train has this occupied block as its valid next block:

    advance that train

Set:

    CurrentBlockId = newlyOccupiedBlockId
    ActiveRouteIndex++

Raise a train-location state change so the WPF UI refreshes immediately.

If ZERO trains match:
- leave the anonymous occupancy in CtcBlockState
- do not move any train
- do not throw merely because an occupancy cannot be identified

There can legitimately be occupied blocks that CTC cannot currently associate
with one of its dispatched trains.

If MORE THAN ONE train matches:
- DO NOT GUESS
- do not move either train
- preserve the occupancy state
- keep their existing CurrentBlockIds

If useful within the current status/event architecture, emit a diagnostic or
dispatcher-readable warning that the occupancy is ambiguous, but do not add a
major new alert framework solely for this feature.
