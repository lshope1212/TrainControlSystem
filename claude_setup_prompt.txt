# PART 1 — UML STYLE / LEVEL OF ABSTRACTION

These diagrams are for a software engineering design review.

The UML should be useful as **design documentation**, not as an exhaustive reproduction of every method call.

Follow these principles:

- The use case diagram should act as a high-level graphical table of contents of CTC functionality.
- Use cases should represent meaningful actor goals, not individual UI buttons.
- External modules may be UML actors because they interact with the CTC system boundary.
- Sequence diagrams should show the important objects/services involved in accomplishing each use case.
- Do not include every property getter, binding update, collection refresh, or trivial helper method.
- Use actual class names from the repository when appropriate.
- Avoid inventing classes that do not exist unless the participant represents an external system actor.
- Keep diagrams readable.
- Prefer approximately 4–7 meaningful lifelines per sequence diagram where possible.
- Use activation bars where appropriate.
- Use return messages only where they add useful information.
- Use `alt`, `opt`, or `loop` interaction fragments only where they materially clarify behavior.
- Do not turn sequence diagrams into algorithm flowcharts.

The codebase should be the main authority for implementation behavior.

# USE CASES

Instead of modeling every button as a separate use case, use these five high-level use cases.

## UC1 — Prepare Schedule

Primary actor:

`Dispatcher`

This use case covers:

- generating a schedule template,
- entering train timing information,
- setting/overriding dwell times,
- uploading a CSV schedule,
- clearing the editable schedule,
- reviewing the schedule before queueing.

Do NOT make Generate Template, Upload Schedule, and Clear Template three unrelated top-level sea-level use cases.

They are alternative actions/scenarios inside the larger dispatcher goal of preparing a schedule.

---

## UC2 — Queue and Automatically Dispatch Trains

Actors:

- Dispatcher
- System Clock
- Track Controller

This covers:

- queueing a completed schedule,
- validating scheduled trains,
- ordering trains by departure time,
- automatic time-triggered dispatch,
- checking whether the start block is usable,
- calculating suggested speed and authority,
- sending the movement information externally,
- moving a train from queued to dispatched state.

Important:

There is deliberately **no normal "Dispatch Train" button**.

The system uses scheduled departures and the dispatch queue.

The train is automatically eligible for release when:

`DepartureTime <= SystemTime`

The Track Controller is involved because dispatch causes movement information to be sent outside CTC.

## UC3 — Monitor Territory and Train Operations

Actors:

- Dispatcher
- Track Controller
- Track Model
- System Clock

This covers the dispatcher observing:

- block occupancy,
- maintenance state,
- switch state,
- signal state,
- crossing state,
- tickets sold/hour,
- queued trains,
- dispatched trains,
- current/inferred train locations,
- suggested speed,
- suggested authority,
- active movement plan,
- target destination,
- arrival time,
- dwell state,
- movement status.

The Track Controller provides block-status information.

The Track Model provides ticket-sales information.

The System Clock drives time-dependent state such as dwell completion.

---

## UC4 — Manage Track Maintenance and Switches

Actors:

- Dispatcher
- Track Controller

This covers:

- enabling maintenance mode,
- closing a block,
- reopening a block,
- changing the position of a switch,
- receiving confirmation/status from the Track Controller.

Maintenance Mode itself is a local CTC operator mode.

Turning maintenance mode on does NOT directly change track state.

Actual block/switch requests are sent to the Track Controller.

---

## UC5 — Update Active Movement Plan

Actors:

- Dispatcher
- Track Controller

This covers changes to an already-dispatched train.

The dispatcher can modify a selected stop's:

- destination block,
- planned arrival time,
- dwell time.

The CTC then recalculates whatever is affected, including:

- route,
- suggested speed,
- suggested authority,
- timing.

Updated movement information is sent externally.

This is one of the most important newer pieces of CTC functionality and should be clearly represented.

## Main flow

1. Track Controller sends `BlockStatusMessage`.
2. `CtcNamedPipeReceiver` receives/deserializes/routes the message.
3. Receiver calls `CTCService.ApplyBlockStatus(...)`.
4. CTC updates the matching block's:
   - occupancy,
   - signal,
   - switch,
   - crossing,
   - confirmed maintenance state.
5. CTC invokes `TrainLocationTracker` using the new occupancy transition.
6. Tracker determines whether a dispatched train can be advanced to the newly occupied block.
7. If a train moved, CTC updates the dispatched train's inferred current block.
8. `MovementPlanner` determines whether the train has reached a scheduled stop and therefore entered Arrived/Dwelling state.
9. CTC raises/causes state updates.
10. `MainWindowViewModel` refreshes the block/train presentation.
11. Dispatcher observes the new status.

### `[occupancy could match multiple trains]`

# PART 4 — DWELL / MOVEMENT BEHAVIOR

Where relevant in the automatic dispatch or monitoring diagrams, correctly represent the current dwell logic.

A dispatched train can conceptually move through:

`En Route → Arrived → Dwelling → En Route`

or eventually:

`→ Completed`

When a train reaches a scheduled destination with dwell time:

1. its arrival is detected,
2. dwell begins,
3. it remains dwelling until the external system time reaches the ready-to-depart time,
4. CTC calculates/sends the suggestion for the next movement,
5. train continues toward the next planned stop.

Do not imply that CTC recalculates speed and authority every time the train simply moves from one ordinary block to another.

The current implementation recalculates/sends movement suggestions at meaningful movement-plan transitions such as:

- initial dispatch,
- dispatcher re-planning,
- starting the next movement after a planned stop/dwell.
