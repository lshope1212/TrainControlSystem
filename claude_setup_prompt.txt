You are working in the TrainControlSystem repository:

https://github.com/lshope1212/TrainControlSystem

Please inspect the current repository before making changes. The most complete/current CTC implementation is on the `Luke_CTC` branch, so use that implementation as the basis for the CTC timing work unless the same changes have already been merged elsewhere.

The purpose of this task is to finalize the simulation timing architecture for full system integration.

# Overall requirement

The system must have ONE authoritative simulation clock.

The CTC must be the ONLY operational module that is allowed to control simulation time.

However, the clock mechanism itself does NOT need to live exclusively inside the CTC. In fact, the preferred architecture is:

CTC controls the simulation clock.

A shared simulation clock service owns and advances authoritative simulation time.

All modules that need time receive the same authoritative simulation time.

Modules other than CTC must NOT independently pause, resume, reset, set, or change the speed of simulation time.

TestUI projects may continue to manually inject timing information for isolated testing, but this must clearly remain test-only functionality.

The goal is to end up conceptually with:

CTC
  |
  | clock control
  v
Shared Simulation Clock
  |
  | authoritative time updates
  +----> CTC
  +----> Train Model
  +----> Train Controller
  +----> Track Model
  +----> Track Controller
  +----> MBO
        as needed

Do NOT unnecessarily couple the clock implementation to CTC.Core business logic.

# Important existing behavior to preserve

Before changing anything, inspect the current timing implementations.

There are already useful pieces that should be preserved.

## CTC

The CTC currently consumes:

`SystemTimeMessage`

and ultimately calls:

`CTCService.SetSystemTimeAsync(TimeSpan systemTime, ...)`

The CTC intentionally does not interpolate time itself.

That method currently uses simulation time to:

- update CTC system time
- release queued trains when `DepartureTime <= SystemTime`
- finish dwell periods
- begin subsequent movement-plan legs
- recalculate movement timing/suggested speeds where appropriate

This timing-driven CTC behavior should remain intact.

Do NOT reintroduce independent CTC timers into CTC.Core for dispatch/dwell logic.

The CTC should continue reacting to authoritative clock updates.

## Train Model

The Train Model currently has a useful fixed-step simulation design in:

`TrainModel.Core/Simulation/SimulationClock.cs`

The important design concept is:

- physics timestep stays fixed, currently approximately `0.1 s`
- playback speed is independent of the physics timestep
- accelerated simulation should run MORE fixed-duration physics steps rather than increasing `dt`

Preserve this fixed-step physics approach.

For example, if 0.5 simulated seconds have elapsed, the Train Model should ideally perform five 0.1-second physics steps rather than one 0.5-second physics step.

Do NOT change the Train Model to use a large variable timestep simply because simulation speed increases.

# Current problem

At present there are effectively two independent clocks.

The CTC TestUI currently acts as a clock source and sends `SystemTimeMessage` to CTC.

Meanwhile, the real Train Model owns its own `SimulationClock`, including:

- pause/resume
- speed multiplier
- elapsed time
- local timing progression

The Train Model's real named-pipe receiver currently does not properly participate in the shared `SystemTimeMessage` architecture.

This means the CTC and Train Model can disagree about time and playback speed.

This must be corrected.

# Desired architecture

Implement the following logical separation:

## 1. Clock authority

Only CTC may REQUEST changes to simulation time.

CTC should be allowed to control:

- Run / Resume
- Pause
- Simulation speed multiplier
- Simulation time / starting time where appropriate
- Reset if reset remains part of the timing UX

No other real operational module may issue these commands.

## 2. Clock mechanism

Create a shared/system-level simulation clock service.

Preferred location:

`TrainControl.Common/Timing`

or another appropriate Shared location after inspecting the architecture.

The lifetime may be hosted by the Launcher if that best fits the current application-launch architecture.

Do not put the full central clock implementation into `CTC.Core`.

Conceptually introduce something like:

`SimulationClockService`

and, where useful, interfaces such as:

`ISimulationClockController`

and/or

`ISimulationClockSource`

The exact naming is flexible if a cleaner convention already exists in the repository.

The important architectural rule is:

CTC gets clock CONTROL capabilities.

Other modules only get clock STATE / TIME information.

## 3. Authoritative time broadcast

The clock should produce authoritative system-time updates that interested modules can consume.

The existing `SystemTimeMessage` should remain the shared clock-state contract unless there is a compelling compatibility reason to introduce a replacement.

Extend it so it carries sufficient timing state.

At minimum it should contain:

```csharp
public TimeSpan SystemTime { get; set; }
public double SpeedMultiplier { get; set; }
public bool IsPaused { get; set; }
```

You may add a monotonically increasing tick/sequence identifier if it meaningfully improves robustness, but do not add unnecessary complexity.

For example:

```csharp
public long Sequence { get; set; }
```

would be acceptable but optional.

Update comments/documentation so `SystemTimeMessage` clearly represents authoritative simulation-clock state distributed system-wide.

# Clock-control contract

Introduce a separate logical contract for requesting clock changes.

Something along the lines of:

```csharp
public class SimulationTimeControlMessage
{
    public SimulationClockCommand Command { get; set; }
    public double? SpeedMultiplier { get; set; }
    public TimeSpan? SystemTime { get; set; }
}
```

or another clean design.

Possible commands include:

- Run
- Pause
- SetSpeed
- SetTime
- Reset

You do NOT have to use this exact class shape if a cleaner strongly typed implementation fits the codebase better.

The important distinction is:

`SimulationTimeControlMessage`
CTC -> central clock

`SystemTimeMessage`
central clock -> modules

Do not overload `SystemTimeMessage` as both a control command and a clock-state notification.

# CTC changes

Add real timing controls to the actual CTC WPF application, not just CTC.TestUI.

The CTC interface should allow the dispatcher to control simulation timing.

At minimum provide:

- current simulation time display
- Run / Resume
- Pause
- simulation-speed selection/control
- current simulation-speed display

If practical and consistent with the current design, also retain:

- Set Time
- Reset

The exact UI layout should fit naturally into the existing CTC window.

Do not redesign the entire CTC UI.

Use the existing MVVM pattern.

The real CTC should SEND clock-control requests rather than simply changing its own local state.

For example:

CTC user clicks `5x`

CTC sends/request:
`SetSpeed(5)`

Shared clock changes to 5x.

Shared clock then publishes authoritative clock state.

CTC receives the resulting `SystemTimeMessage`.

CTC updates its displayed time/state from that authoritative message.

This avoids CTC pretending that a request succeeded before the shared clock actually changes.

# Train Model changes

This is a major part of the task.

The real Train Model must no longer independently own simulation speed as an operator-controlled concept.

Its current physics system should remain fixed-step.

Refactor the Train Model so its progression follows authoritative simulation time.

The preferred conceptual behavior is:

Receive new authoritative system time.

Compare:

`newSystemTime - previousSystemTime`

Determine how much simulated time elapsed.

Run the appropriate number of fixed physics steps.

Example:

Previous system time:
`12:00:00.0`

New system time:
`12:00:00.5`

Elapsed simulated time:
`0.5 seconds`

Physics timestep:
`0.1 seconds`

Train Model executes:

5 x `Step(0.1 seconds)`

The fixed timestep should remain stable even at accelerated simulation speeds.

Handle fractional remainder safely if incoming simulated-time deltas do not divide perfectly by `dt`.

For example, maintain a simulation-time accumulator.

Do not accumulate error unnecessarily.

# Train Model pause behavior

If the authoritative clock is paused, simulation time should not advance.

The Train Model therefore should perform no physics progression while paused.

It should not need its own independent pause timer.

# Train Model speed behavior

The Train Model should not determine speed itself in integrated operation.

The authoritative clock advances simulated time faster at higher playback multipliers.

The Train Model simply processes whatever amount of SIMULATED time has elapsed.

For example, if the central clock runs at 5x and sends enough updates that 0.5 simulated seconds elapsed since the prior message, Train Model performs five 0.1-second steps.

The Train Model does not need to know "run physics 5x faster" independently if system-time deltas already encode that progression.

It may still display:

- system time
- current speed multiplier
- paused/running state

from the received `SystemTimeMessage`.

# Remove independent timing authority from Train Model WPF

The real Train Model currently has controls such as:

- Play/Pause
- SpeedMultiplier

For the real integrated Train Model WPF application:

either remove these controls or make them read-only displays.

Preferred result:

`TrainModel.TestUI.Wpf`

# Initial synchronization

Handle the first received `SystemTimeMessage` safely.

The first clock message should establish a baseline and should NOT cause the Train Model to suddenly simulate from `00:00:00` to the current clock time.

For example:

first message:
`12:00:00`

should set:

`lastSystemTime = 12:00:00`

without simulating twelve hours.

Only subsequent deltas should advance physics.

# Time moving backward

Handle backward clock movement explicitly.

For normal simulation, time should generally move forward.

If a TestUI or reset operation causes time to move backward:

- do not run negative physics
- reset/rebaseline the Train Model's timing accumulator appropriately
- do not attempt to reverse physical simulation

Similarly, preserve the current CTC behavior where moving time backward does not "un-dispatch" trains.

Document this behavior.

# Central clock update frequency

The current CTC TestUI updates once per second.

For final integration, use a substantially finer central timing interval.

A target around 100 ms is appropriate unless the repository architecture strongly suggests another interval.

Example behavior:

At 1x:
every 100 ms real time -> approximately +0.1 simulated seconds

At 5x:
every 100 ms real time -> approximately +0.5 simulated seconds

At 10x:
every 100 ms real time -> approximately +1.0 simulated second

Do NOT increase the Train Model physics timestep when running faster.

Avoid relying on the WPF timer interval itself as exact simulation time.

Prefer using actual elapsed wall-clock duration, such as `Stopwatch`, then multiply that by playback speed to calculate how much simulated time should advance.

This prevents drift when the UI thread is briefly delayed.

# Important transport consideration

The current transport appears oriented around named destinations such as individual module pipes.

Do not create a fake "broadcast" abstraction if the transport does not support real broadcasting.

It is acceptable for the central clock publisher to send the same `SystemTimeMessage` individually to:

- CTC pipe
- Train Model pipe
- other subscribed module pipes

Conceptually this is still a clock broadcast.

Keep this implementation simple and explicit.

# Failure isolation

A clock update failing to reach one module should not freeze the entire simulation clock.

For example, if Train Model is not running:

- log/report the failed Train Model send
- continue advancing system time
- continue sending updates to CTC and other active modules

Do not make one disconnected module block the global timing loop.

Likewise, avoid overlapping clock publishes if a previous publish is still stalled.

Use cancellation tokens appropriately on application shutdown.

# Message ordering

Clock messages should be applied sequentially inside each module.

Avoid concurrently processing multiple time messages in a module if doing so could reorder simulated-time progression.

The CTC currently serializes inbound named-pipe handling onto its UI thread.

Preserve safe ordering.

For the Train Model, ensure time messages cannot cause overlapping physics advancement.
