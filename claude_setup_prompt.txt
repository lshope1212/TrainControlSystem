PART C — DEFINE TRAIN POSITION SEMANTICS

The Train Model owns physical motion, not the route geometry.

PositionMeters is:
- A cumulative distance traveled since dispatch.
- Initialized to 0 when activated.
- Integrated from velocity by the existing simulation physics.
- Independent of line or block numbering.
- Measured in meters.
- Representing the FRONT of the train, consistent with the current Train model.

This is NOT:
- The current block number.
- An absolute map coordinate.
- A distance within the current block.
- A position value reset at each block boundary.

The Train Model should not know block lengths, switch topology, or route-to-block calculations.

PART E — TRACK MODEL POSITION-TO-BLOCK MAPPING

The Track Model must translate cumulative position into occupancy using the per-train route recorded at placement.

Example:

Block A: 100 meters
Block B: 75 meters
Block C: 120 meters

A train dispatched at the beginning of Block A reports:

PositionMeters = 115

The train's FRONT has traveled 115 meters.

Therefore its front is 15 meters into Block B.

For a 32.2-meter train:

Front = 115
Rear = 115 - 32.2 = 82.8 meters.

The train occupies both Block A and Block B.

Required implementation:

1. Maintain per-train tracking state in TrackModel.Core:
- Train ID
- Line ID
- Starting block ID
- Ordered traversed/assigned route
- Latest cumulative front position
- Train length
- Current head block / route index
- All currently occupied blocks
- Latest processed telemetry tick

2. Calculate the cumulative route boundaries using actual block lengths from the loaded layout.

Use the ordered route, not numerical block IDs.

3. Calculate train footprint:
Front = PositionMeters
Rear = PositionMeters - TrainLengthMeters

Determine every block intersected by the train's physical footprint.

At dispatch, PositionMeters = 0 should occupy the starting block. The initially negative rear position represents the portion still in the yard/outside the modeled route; do not incorrectly mark a preceding line block occupied.

4. Update occupancy atomically.

A block becomes occupied when the train's front enters.

A trailing block remains occupied until the train's rear fully leaves it.

A train may occupy two or more blocks, especially if a train is longer than an individual block.

Only clear a block when the train no longer physically occupies it.

5. Support multiple trains on a line.

Maintain occupancy ownership internally so one train cannot incorrectly clear a block belonging to another.

Reject conflicting placements and unsafe occupancy claims.

6. Reject invalid position telemetry.

Handle:
- NaN/infinity
- Negative distance
- Nonpositive or invalid train length
- Unknown train ID
- Telemetry received before placement
- Stale or out-of-order tick IDs
- Impossible backward jumps
- Position exceeding the valid route
- Unexpected discontinuities and reset conditions

Invalid telemetry must not silently move a train or clear occupied blocks.

7. Handle route topology and switches correctly.

Do not assume GREEN-1, GREEN-2, GREEN-3 is necessarily a valid route.

A train's path must use valid track connections and valid switch branches.

Physical occupancy must reflect the path actually traversed. The current switch alignment must not be silently ignored in favor of a desired route.

If a switch or route cannot be reconciled safely, report an error and fail safely rather than inventing movement.

Keep this compatible with CTC's existing route-replanning feature. If a future path changes while the train is moving, previously traveled distance must remain valid; never reset PositionMeters or reinterpret already traversed blocks.

Implement the necessary route-update coordination or explicitly handle such changes safely without silently continuing along a stale route.
