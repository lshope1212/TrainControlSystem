## Goal

Implement the real **Graphical Territory Overview** for the CTC module.

The CTC currently has a large placeholder area labeled `Territory Overview` in:

`src/CTC/CTC.Wpf/MainWindow.xaml`

This needs to become an interactive schematic track map for the currently selected line.

The dispatcher must be able to:

- visually inspect the topology of the selected line;
- visually inspect block occupancy and maintenance state;
- see stations, switches, signals, and railway crossings;
- see the current switch/signal/crossing state where applicable;
- click a block on the map to make it `SelectedBlock`;
- select the same block from the existing block dropdown;
- have map selection and dropdown selection remain synchronized;
- change between Blue, Red, and Green using the existing Current Line selector.

The existing dropdown must remain. The graphical territory map is an additional and preferably primary way to select blocks.

Do **not** implement the final Track Model ↔ CTC communication as part of this task. We will do that separately afterward.

# 1. Create a CTC-specific territory map control

Create something along the lines of:

`src/CTC/CTC.Wpf/Controls/CtcTerritoryMap.cs`

```text

        ↓

        ↓
existing right-side Selected Block inspector changes
```

The reverse must also work:

```text
Dropdown selection changes
        ↓
SelectedBlock changes
        ↓
matching map block gets selected/highlighted
```

Do not create a second independent selected-block state.

`MainWindowViewModel.SelectedBlock` remains the authoritative selection.

# 4. Create a presentation-only layout engine

Do NOT put hundreds of X/Y coordinates into `CtcBlockState` or the shared track contract.

Create a WPF-side layout component, for example:

```text
CTC.Wpf/Layout/TerritoryLayoutEngine.cs
CTC.Wpf/Layout/TerritoryLayoutProvider.cs
CTC.Wpf/Layout/TerritoryBlockPlacement.cs
```

Exact names are flexible.

The layout engine should generate schematic coordinates for each block based on:

- selected line;
- section;
- block number/order;
- actual `ConnectedBlockIds`.

## Desired approach

Use the workbook's section-level track diagram as the reference.

Define presentation-only section paths for:

- Blue A/B/C
- Red A–T
- Green A–Z

Then distribute the blocks belonging to each section along that section's path in block-number order.

A section path may simply be represented as a line/polyline with normalized points.

For example, Blue should visually resemble:

```text
YARD -- A1 -- A2 -- A3 -- A4 -- A5
                                /   \
                               /     \
                          B6-B7-...-B10
                               \
                                C11-C12-...-C15
```

Do not necessarily render Yard as a real selectable `CtcBlockState`; a visual-only Yard terminal label is fine.

For Red and Green, recreate the recognizable section-level loops/branches shown in the workbook's `Track Layout` diagram, and distribute the individual blocks along those paths.

This gives us an accurate course-layout schematic without contaminating the shared domain objects with UI coordinates.

## Important

Actual block-to-block connection lines must ultimately use:

```csharp
ConnectedBlockIds
```

from the loaded layout.

Do not infer runtime topology solely from adjacent block numbers.

The section geometry determines **where to draw things**.

`ConnectedBlockIds` determines **what is actually connected**.

Deduplicate undirected connections so an A↔B relationship is drawn once.

If an unknown/future line or section is loaded for which no custom section geometry exists, provide a reasonable generic fallback layout instead of crashing.

# 5. Visual design of each block

The map must communicate live CTC state clearly without becoming unreadable.

Use the current CTC visual language: clean, technical, light gray/white background, compact railway-control schematic.

## Occupancy

Use the main block body fill:

- Clear / unoccupied = green
- Occupied = red
- Unknown = gray

Use subdued colors similar to the Track Controller map rather than excessively bright colors.

## Maintenance

If a block is confirmed closed for maintenance:

- orange outline around the block;
- optionally an `M` badge.

A pending requested maintenance state may optionally use a dashed orange outline if this can be done cleanly.

Do not confuse a CTC request with Track Controller confirmed state.

## Selection

Selected block:

- strong blue outline outside the normal block rectangle;
- must remain obvious regardless of occupancy fill.

## Switches

Blocks containing switches must be visually obvious.

Use a compact switch/turnout symbol or badge and display its current reported position:

```text
SW N
SW R
SW ?
```

where `?` means Unknown.

The connecting track geometry should make the branch visually understandable.

## Signals

If `HasSignal`:

draw a small signal indicator beside the block.

Colors:

- Red = red
- Yellow = yellow/gold
- Green = green
- Super Green = brighter distinct green
- Unknown = gray

The map should communicate the signal state with both color and, at usable zoom levels, a short text or tooltip so it is not color-only.

## Railway crossings

If `HasCrossing`:

show a crossing symbol/badge and its state:

```text
XING OPEN
XING CLOSED
XING ?
```

A compact version is fine on the map as long as the full value is available through hover/selection.

## Stations

If `StationName` is not empty:

display the station name near the appropriate block.

Stations should visually stand out from ordinary blocks but must not obscure status indicators.

## Block labels

Every block should at least display its human-readable section + block number:

```text
A1
C7
H35
W132
```

# 7. Live updates

This is critical.

The map must update when the existing CTC state changes.

Example:

```text
BlockStatusMessage arrives
        ↓
CTCService.ApplyBlockStatus(...)
        ↓
CtcBlockState changes
        ↓
BlockViewModel.Refresh()
        ↓
graphical block redraws automatically
```

Do not require the dispatcher to switch lines, reselect a block, or reload the layout to see a new occupancy/signal/switch/crossing status.

Because `Blocks` itself may not be replaced for every status update, ensure the custom map invalidates itself when contained `BlockViewModel` items raise `PropertyChanged`.

Manage subscriptions properly when the block collection changes so there are no stale subscriptions or memory leaks.
