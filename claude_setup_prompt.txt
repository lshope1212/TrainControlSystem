Repository:
https://github.com/lshope1212/TrainControlSystem

Work against the current `Luke_CTC` branch and inspect the existing implementation carefully before making changes.

The CTC already supports:
- building schedules
- queueing trains
- dispatching trains automatically based on system time
- calculating an initial suggested speed
- calculating an initial suggested authority
- sending a `MovementSuggestionMessage`
- sending a `MovementRequestMessage`
- displaying dispatched trains
- storing `LastKnownBlockId`

We now need to support **manual modification/rerouting of a train AFTER it has already been dispatched**.

# Required behavior

Once a train is in the "Dispatched Trains" area, the dispatcher must be able to select it and modify its current movement plan.

There are two main cases:

1. Change the arrival time while keeping the same destination block.
   - Example: Train 000 was supposed to reach Block D12 at 12:15:00.
   - Dispatcher changes this to 12:18:00.
   - CTC must recalculate the suggested speed required to reach D12 at the new time.
   - Suggested authority must also be recalculated from the train's current/last-known location along the active route.
   - Send the new suggestion to the Track Controller.

2. Change the destination block.
   - Example: Train 000 was heading to D12 but the dispatcher changes its destination to F6.
   - CTC must determine a route from the train's current/last-known block to F6.
   - Recalculate suggested speed based on the destination and target arrival time.
   - Recalculate authority based on the newly selected route and current block conditions.
   - Send the new suggestion to the Track Controller.

The dispatcher should be able to change BOTH destination and arrival time at once as well.

Do NOT make suggested speed or suggested authority directly editable. The dispatcher edits the movement objective (destination/time), and CTC calculates speed and authority.

# Important current limitation

Currently `DispatchedTrainState.LastKnownBlockId` is initialized to the train's starting block when it is dispatched.

The comments correctly explain that CTC cannot yet update this position accurately because ordinary block occupancy messages do not contain a TrainId.

Do NOT try to solve or guess train position as part of this task.

For now:
- use `LastKnownBlockId` as the starting block for post-dispatch calculations
- clearly preserve/document this limitation
- design the code so that when `LastKnownBlockId` begins receiving real live train-position updates later, no rerouting logic needs to be rewritten

In other words:

    route calculation:
    LastKnownBlockId -> selected destination

Eventually LastKnownBlockId will represent the actual train position.

# 2. Generalize SpeedPlanner

Inspect:

`CTC.Core/Dispatching/SpeedPlanner.cs`

Currently `CalculateInitialSpeed()` calculates:

route start -> next timed scheduled block

using:

distance / (targetArrivalTime - currentSystemTime)

We now need equivalent functionality for an already-dispatched train.

Add a reusable method that can calculate a speed suggestion given:

- a route/path beginning at the train's current/last-known block
- a target arrival time
- current CTC system time

Conceptually:

    remainingSeconds = targetArrivalTime - currentSystemTime
    requiredSpeed = routeDistance / remainingSeconds
    permittedSpeed = minimum applicable block speed limit and train maximum
    suggestedSpeed = min(requiredSpeed, permittedSpeed)

Reuse existing helpers where appropriate. Do not duplicate the unit-conversion and speed-limit logic.

The initial-dispatch code should ideally continue to reuse the same underlying calculation logic.

Handle these cases cleanly:

- arrival time is in the future and achievable
- arrival time is in the future but would require exceeding the permitted maximum
- arrival time has already passed
- destination cannot be reached
- route contains a block with an invalid/no speed limit

For a requested arrival time that cannot be achieved without exceeding the permitted maximum:
- do NOT issue an unsafe speed
- clamp the suggestion to the maximum permitted speed
- return/provide a dispatcher-readable warning stating that the requested arrival time cannot be met

Likewise, if the requested arrival time has already passed, suggest the maximum legal speed and provide a warning.

Do not ever exceed track/train speed limits.

# 4. Generalize AuthorityManager

Inspect:

`CTC.Core/Dispatching/AuthorityManager.cs`

Currently authority is described and implemented as "initial authority."

Generalize it so that the same fixed-block authority calculation can also be used after dispatch.

For a rerouted train, authority should be calculated along:

    LastKnownBlockId -> selected destination

using the new route.

It must continue to stop authority before:
- occupied blocks
- blocks confirmed closed for maintenance
- blocks CTC has requested closed

IMPORTANT:

When performing a post-dispatch calculation, the train's current block may itself be reported as occupied because THAT TRAIN is occupying it.

Do not cause the train to receive zero authority simply because its starting/current block is occupied by itself.

For reroute calculations, treat the starting/current block as the train's own block and evaluate unsafe occupancy beginning with blocks AHEAD of it.

Keep the logic conservative and document this assumption.

We do not know the train's exact position within the block yet, so continuing to use block-level distance is acceptable for this iteration.
