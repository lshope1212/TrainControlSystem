# Fix Simulation Stuttering and Track Controller Performance

You are working in the `TrainControlSystem` C#/.NET/WPF repository.

**Repository:** https://github.com/lshope1212/TrainControlSystem

**Branch:** `Luke_CTC` — use the latest available changes.

## Objective

Investigate and fix a performance regression that causes the entire TrainControlSystem simulation to stutter briefly while a train is moving.

**Important: The Green Line Edgebrook use case is now working correctly. Preserve that functionality.**

The objective is to improve performance and responsiveness without changing the existing movement, routing, authorization, or safety behavior.

## 1. Description of the problem

We recently got the full Green Line use case working:

- Train 001 dispatches from the Green Line yard at GREEN-63.
- The CTC calculates the route to Edgebrook (GREEN-9).
- The Track Controller coordinates all necessary waysides, grants authority, and automatically changes switches.
- The Track Model and Train Model propagate the train's movement.
- The train successfully reaches Edgebrook.

However, following recent changes to the Track Controller by a teammate, the simulation has become noticeably laggy.

**Observed behavior:**
- While the train is moving, the system periodically freezes for a fraction of a second.
- The system clock displayed in the application also appears to momentarily freeze.
- The train continues moving successfully, but the simulation feels choppy.
- These small delays appear to accumulate, making the entire movement simulation take longer than expected.
- The issue is particularly noticeable when a train is actively propagating through the system.

The system is functionally correct. This task is strictly focused on resolving performance problems.

## 2. Investigate likely performance bottlenecks

The following concerns were identified during a preliminary repository review. Verify them rather than assuming they are all responsible.

### A. Excessive Track Controller evaluations

Inspect:

`src/TrackController/TrackController.Core/Services/TrackControllerService.cs`

Specifically, `GetSnapshot()` currently calls `Reevaluate()` on every invocation.

Inspect:

`src/TrackController/TrackController.Core/Services/TrackControllerService.Evaluation.cs`

Determine how expensive `Reevaluate()` is, particularly when all configured waysides must repeatedly:

- Scan track-block feedback.
- Compute switch alignment demands.
- Evaluate movement requests.
- Run the vital PLC program.
- Check route safety and authorization.
- Generate complete snapshots.

Investigate whether identical, unchanged inputs are causing the same expensive evaluation to be performed repeatedly.

Avoid unnecessary evaluation without sacrificing timely safety decisions, watchdog expirations, or authority revocations.

### B. Duplicate polling across coordinated waysides

Inspect:

`src/TrackController/TrackController.Runtime/TerritoryRuntimeRouter.cs`

Pay particular attention to `PollAllAsync()`.

The current implementation calls `PollAsync()` on all territories and then performs a second polling pass over local territories.

Since local runtime polling invokes `TrackControllerService.GetSnapshot()`, this appears to cause redundant evaluations.

Also inspect `ReceiveAsync()`, which invokes `PollAllAsync()` in its `finally` block, including after operations that may already have updated the runtime snapshots.

Determine:

1. How many complete PLC evaluations occur per message and per second.
2. Whether all 16 waysides really need reevaluation after every received message.
3. Whether repeated polling can be eliminated while retaining the latest coherent snapshot and coordinated safety approvals.
4. Whether the router's `_operations` semaphore is held unnecessarily long, delaying incoming messages and other publishers.

Optimize this behavior where appropriate.

Do not compromise the joint approval process between waysides.

### C. Unnecessary evaluation during message processing

Inspect:

`src/TrackController/TrackController.Runtime/LocalWaysideRuntime.cs`

The runtime currently refreshes its snapshot in the `finally` block of `ReceiveAsync()`.

Some controller operations already call `Reevaluate()` internally, so the additional snapshot request may repeat the evaluation.

Find a safe way to avoid redundant work while maintaining up-to-date outputs.

### D. Excessive publisher polling

Inspect:

`src/TrackController/TrackController.Wpf/Services/WaysidePipeHost.cs`

The production host has separate publishers for:

- CTC status updates.
- Track Model commands.
- Monitor diagnostics.

These publisher loops can independently request full runtime polls, even when the evaluated state is unchanged.

Investigate whether they are multiplying the workload unnecessarily.

Possible improvements include:

- Sharing safely evaluated immutable snapshots between publishers.
- Avoiding duplicate evaluations when nothing has changed.
- Coalescing redundant periodic work.
- Separating diagnostic publication from safety-critical evaluation.
- Reducing unnecessary allocations and serialization.

Maintain prompt delivery of changed or revoked movement authority. Do not introduce a delay in safety-critical commands just to reduce CPU usage.

### E. WPF UI updates and rendering

Inspect:

`src/TrackController/TrackController.Wpf/ViewModels/MainWindowViewModel.cs`

and

`src/TrackController/TrackController.Wpf/Controls/TerritoryMap.cs`

The operator UI currently refreshes every 250 ms.

Investigate whether every refresh unnecessarily:

- Rebuilds movement and equipment row collections.
- Raises property change notifications for unchanged data.
- Recomputes territory maps and block lists.
- Triggers full WPF redraws.
- Allocates brushes, pens, geometries, or formatted text.

Reduce unnecessary UI work and cache immutable rendering resources where useful.

The UI should remain responsive during train movement, even when the underlying waysides are evaluating complex routes.

Keep heavy evaluation off the UI thread.

### F. Shared simulation clock

Inspect:

`src/Launcher/TrainControlSystem.Launcher.Wpf/Services/SimulationClockHost.cs`

Determine whether the authoritative simulation clock is genuinely experiencing delays or whether its displayed updates are being delayed by other processes.

Inspect the relevant Train Model and CTC clock consumers as necessary.

Do not replace or redesign the shared clock unless the investigation demonstrates a clock-specific defect.

The existing simulation timing semantics should be preserved, including the ability to run at 1x through 10x speed.

## 3. Measure the problem before implementing major changes

Add lightweight, development-only performance diagnostics as needed.

Use `Stopwatch` or another suitable low-overhead mechanism.

At minimum, investigate:

- Duration of a complete Track Controller reevaluation.
- Number of reevaluations per second, per wayside.
- Duration of `TerritoryRuntimeRouter.PollAllAsync()`.
- Duration of processing Track Model feedback and CTC movement messages.
- Time spent waiting for the router's operation semaphore.
- Duration and frequency of UI refreshes.
- Actual delivery cadence of simulation clock updates.

Measure under the normal 16-wayside course deployment, preferably with an active Green Line train.

Distinguish between:
- CPU-bound computation.
- Lock contention.
- Named-pipe communication delays.
- WPF rendering delays.
- Actual shared-clock timing issues.

Identify the dominant bottlenecks and prioritize fixing those.

Avoid adding noisy logging to every simulation tick in the final production configuration.

## 4. Implement the necessary performance fixes

After determining the causes, implement targeted optimizations.

Prioritize changes in the Track Controller because the regression appeared after recent Track Controller changes.

In general:

1. Eliminate genuinely redundant reevaluation and polling.
2. Avoid repeating identical work across publishers.
3. Reduce unnecessary synchronization and lock contention.
4. Optimize expensive repeated PLC/route computations where measurements justify it.
5. Improve UI refresh efficiency.
6. Preserve correctness of all asynchronous and concurrent operations.

Avoid using arbitrary delays, slowing the simulation clock, or increasing timeout values simply to hide the performance problem.

Do not blindly introduce `Task.Run()` everywhere. Address the actual expensive operations and contention first.

### Critical safety requirements

All existing behavior must be maintained:

- Waysides continue independently evaluating their assigned safety responsibilities.
- Cross-territory movement still requires coordinated approval.
- The Track Controller still automatically aligns switches correctly.
- Signal and crossing protection remains intact.
- Occupancy and feedback freshness are enforced.
- Stale feedback or communication failure causes authority to be withheld.
- Movement authorization is never granted from an incomplete or stale assessment.
- Previously issued authority is not increased unexpectedly.
- Authority withdrawal reaches the Track Model promptly.
- Request and feedback watchdogs continue functioning correctly.
- Train identity and authority handoffs remain correct.

**Do not solve performance problems by removing safety checks or bypassing wayside coordination.**

If caching evaluations or snapshots, ensure a safety-relevant change, timeout, or expiration invalidates the cached result immediately or before it could be used unsafely.
