## Current problem

The CTC UI already contains a `Toggle Switch` button.

The shared contract also already contains:

```csharp
SwitchPositionRequestMessage
```

and `CTCService` already contains:

```csharp
CreateSwitchPositionRequest(string blockId, SwitchPosition requestedPosition)
```

However, the actual dispatcher action is not implemented.

Currently:

1. A track layout can be loaded.
2. A block with a switch can receive an initial switch state through the CTC TestUI.
3. The CTC correctly displays that state.
4. The dispatcher can select that block.
5. The Toggle Switch button can be pressed when allowed.
6. But pressing it sends no outbound message and performs no actual action.

Implement the complete CTC-side switch-request workflow.

# Desired architecture

The flow should be:

```text
CTC UI
   ↓
MainWindowViewModel
   ↓
ICTCService
   ↓
CTCService
   ↓
SwitchPositionRequestMessage
   ↓
IMessageSender
   ↓
Track Controller
```

During isolated testing, the CTC TestUI's fake Track Controller receiver should capture and display the outgoing `SwitchPositionRequestMessage`.

Do NOT have the ViewModel construct shared contract messages directly.

Follow the same architecture already used by `CloseBlockAsync()`.

# 1. Add a switch action to ICTCService

Add an asynchronous dispatcher action such as:

```csharp
Task SetSwitchPositionAsync(
    string blockId,
    SwitchPosition requestedPosition,
    CancellationToken cancellationToken = default);
```

A name such as `RequestSwitchPositionAsync` is also acceptable if it fits the existing naming conventions better.

This is different from:

```csharp
CreateSwitchPositionRequest(...)
```

The existing `Create...` method only builds a message.

The new async method must actually SEND the request using the injected `IMessageSender`.

# 2. Implement the action in CTCService

Implement the new method in `CTCService`.

Conceptually:

```csharp
public async Task SetSwitchPositionAsync(
    string blockId,
    SwitchPosition requestedPosition,
    CancellationToken cancellationToken = default)
{
    var request = CreateSwitchPositionRequest(
        blockId,
        requestedPosition);

    await _messageSender.SendAsync(
        request,
        cancellationToken);
}
```

Reuse the validation that already exists inside:

```csharp
CreateSwitchPositionRequest(...)
```

That validation already ensures:

- the block exists,
- the block actually has a switch,
- the requested position is not `Unknown`.

Do not duplicate validation unnecessarily.

# IMPORTANT: do not optimistically modify the actual switch status

Do NOT simply do this after sending:

```csharp
block.Switch = requestedPosition;
```

The existing `CtcBlockState.Switch` represents:

> the latest wayside switch status reported by the Track Controller

The real architecture should therefore be:

```text
CTC requests Reverse
        ↓
Track Controller receives request
        ↓
Track Controller moves switch
        ↓
Track Controller reports BlockStatusMessage
        ↓
CTC ApplyBlockStatus(...)
        ↓
CtcBlockState.Switch becomes Reverse
        ↓
UI updates
```

The CTC must not claim that the switch physically changed just because its request was successfully transmitted.

For this iteration, when testing CTC in isolation:

1. press Toggle Switch,
2. verify that the TestUI captures the outbound request,
3. then use the TestUI's Block Status input to simulate the Track Controller reporting the resulting switch position,
4. verify that the CTC Block Status display changes.

This separation is intentional.

# 5. Command CanExecute requirements

The Toggle Switch command should only execute when ALL of the following are true:

```text
Maintenance Mode is ON
AND
a block is selected
AND
the selected block has a switch
AND
the current switch position is known
```

So conceptually:

```csharp
private bool CanToggleSelectedBlockSwitch()
{
    return IsMaintenanceMode
        && SelectedBlock is not null
        && SelectedBlock.HasSwitch
        && SelectedBlock.SwitchPosition != SwitchPosition.Unknown;
}
```

Preserve the Maintenance Mode feature that was just added.

The existing behavior must therefore be:

| Maintenance Mode | Has Switch | Switch Known | Button |
|---|---:|---:|---|
| OFF | Yes | Yes | Disabled |
| ON | No | N/A | Disabled |
| ON | Yes | No | Disabled |
| ON | Yes | Yes | Enabled |

Do not remove any XAML-level protections that already exist unless they are redundant and the resulting behavior remains identical.

# 7. Update CommunicationStatus

Use the existing `CommunicationStatus` property so the dispatcher receives useful feedback.

Before sending, something like:

```text
Requesting Block A5 switch Reverse...
```

On success:

```text
Switch position request sent for Block A5: Reverse.
```

On failure:

```text
Unable to send switch request: <reason>
```

Follow the same exception-handling philosophy used by `CloseSelectedBlockAsync()` so a communication failure never crashes the WPF UI.

Example conceptual structure:

```csharp
try
{
    await _ctc.SetSwitchPositionAsync(...);

    CommunicationStatus =
        $"Switch position request sent for Block {block.BlockId}: {requestedPosition}.";
}
catch (Exception ex)
{
    CommunicationStatus =
        $"Unable to send switch request: {ex.Message}";
}
```

Do not change `block.Switch` here.
