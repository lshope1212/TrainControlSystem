# TrainControlSystem — Implement Yard-Restricted Route Starting Blocks

You are working in the TrainControlSystem C#/.NET/WPF repository, on the latest `Luke_CTC` branch.

## Objective

Modify the CTC Schedule Builder so that the dispatcher can **select the starting block for each train's route**, rather than automatically using the lowest-numbered block on the selected line.

However, for realistic train dispatching, **only legitimate yard-entry blocks should be available as starting locations**.

This is a focused change to the existing scheduling workflow. All five modules are already connected, and the existing solution build and integration tests have passed. Preserve that working integration.

## 1. Inspect the current implementation

Before modifying code, examine:

- `ScheduleTemplateFactory.cs`
- `ScheduleTemplate.cs` and `ScheduleTemplateConverter.cs`
- `ScheduleBuilderViewModel.cs`
- `ScheduleTemplateRowViewModel.cs`
- `ScheduleCsvImporter.cs`
- `ScheduledTrain.cs` and `CTCService.QueueSchedule()`
- The CTC Schedule Builder XAML
- Track Model's course layout, importer and layout message contracts
- `TrackLayoutReconciler.cs`
- Existing CTC scheduling and integration tests

Currently, `ScheduleTemplateFactory.GetRouteStartBlock()` assumes that the route starts at the lowest-numbered block.

Remove that assumption from production schedule creation.

## 2. Determine legitimate yard-entry blocks

The actual track layout is authoritative.

The current course network contains the following yard information:

- Blue Line: yard entrance at the beginning of the line, near Block `1`.
- Red Line: yard switch associated with `RED-9`.
- Green Line: yard connections associated with `GREEN-58` and `GREEN-62`, described as `57-yard` and `yard-63`.

**Important:** These references identify yard connections or switches, not necessarily the precise mainline block where a dispatched train should first appear.

Investigate the course track layout and existing documentation to establish the valid mainline starting blocks.

In particular, examine whether `GREEN-57` and `GREEN-63` are the appropriate Green Line yard-entry blocks, rather than simply assuming that switch blocks 58 and 62 must be selected.

Do not arbitrarily classify a block as yard-adjacent merely because it is the first block, contains a switch, or is close to a station.

`GREEN-14` must not be treated as a yard entrance without supporting layout evidence.

### Represent yard-entry information explicitly

Introduce a small, maintainable way for CTC to identify valid yard-entry blocks.

Prefer placing explicit yard-entry metadata alongside the Track Model's authoritative course layout and exposing it through the existing layout message when practical.

A field such as `IsYardEntry` on a block definition is acceptable, as is another clean solution that preserves the existing architecture.

Requirements:

- Preserve the current track geometry and block IDs.
- Do not create fictitious yard blocks.
- Do not modify PLC switch behavior.
- Do not add a direct CTC connection to the Train Model.
- Do not modify existing train physics.
- Preserve compatibility with the three-line layout.
- Ensure imported or revised layouts do not silently invent yard-entry locations.
- If the evidence cannot establish an exact yard-entry block, explicitly report that uncertainty rather than guessing.

The CTC must derive its available starting blocks from the selected line's validated yard-entry information.

If none are defined, show a clear explanation and prevent scheduling until the information is configured.

## 3. Add starting-block selection to the Schedule Builder

Modify the existing CTC Schedule Builder UI.

When the dispatcher creates a schedule template:

1. Select a line (Blue, Red, or Green), as currently supported.
2. Enter the number of trains and generate the schedule template.
3. For each train, choose a starting block from a dropdown containing ONLY that line's valid yard-entry blocks.
4. Enter the departure time for the selected starting block.
5. Enter arrival times at the desired later blocks as before.
6. Queue the schedule using the existing workflow.

### UI requirements

- Provide one starting-block selection per train, not one global selection for every train.
- The dropdown should use readable block labels and actual block IDs.
- If the line has exactly one valid yard entry, selecting it automatically is acceptable.
- If multiple yard entries exist, the dispatcher should be able to choose independently for each train.
- Clearly indicate each train's selected starting block in the schedule grid.
- Only the selected starting block's time should be interpreted as that train's departure time.
- The dispatcher must not be able to select an arbitrary track block as a starting location.
- Preserve the existing spreadsheet-style schedule builder, destination times and dwell-time editing.

Keep the UI relatively simple. A compact starting-block selector associated with each train is preferable to a major Schedule Builder redesign.

## 4. Update schedule conversion and route generation

Currently, the schedule template has a single `IsRouteStart` flag on a block row.

That assumption must be revised to support different starting blocks for different trains.

The new model must:

- Store the selected starting block separately for each train.
- Identify that train's departure time at its selected start block.
- Build that train's route beginning at the correct block.
- Continue using the existing schedule waypoint and route construction system.
- Preserve timed destinations, intermediate untimed blocks and dwell settings.
- Never add unrelated blocks before the selected starting block.
- Preserve the order in which blocks are actually traveled.

The final `ScheduledTrain.Route[0]` must contain the selected start block.

Consequently, `ScheduledTrain.StartBlockId` and the existing `TrainDispatchRequestMessage` should automatically carry the correct starting block without needing a new dispatch protocol.

### Changing an existing selection

If the dispatcher changes the selected starting block after entering schedule times:

- Do not silently misinterpret the old departure time as a destination time.
- Preserve valid user-entered information where practical.
- Clearly identify any schedule times that must be reconsidered.
- Revalidate the resulting route before allowing it to be queued.

### CSV schedules

Ensure the existing CSV schedule import remains usable.

The imported template must support the same yard-entry restrictions and starting-block selections as manually generated templates.

You may add optional starting-block metadata or allow the dispatcher to select the starting block after import.

Do not silently treat an arbitrary first timed block as a valid yard entry.

Preserve backward compatibility where the starting block can be determined unambiguously from the valid yard entries. Otherwise require explicit selection.

## 5. Validate the selected starting block

Add appropriate checks in CTC.Core, not only in the WPF UI.

A schedule should be rejected if:

- The starting block is missing.
- The starting block is on a different line.
- The starting block is not an approved yard entry.
- The route does not begin at the selected starting block.
- The route contains disconnected blocks.
- A timed destination is unreachable through the existing route planner.
- A departure time is missing or invalid.

Use dispatcher-readable error messages.

Continue using the existing live occupancy, maintenance and safety checks when the train is actually released.

Do not reserve or occupy the selected starting block merely because it appears in a schedule. Physical placement must still happen through the existing dispatch integration.

### Routing limitations

The existing CTC shortest-path logic does not account for every one-way travel restriction or physical switch constraint.

Do not unnecessarily redesign the entire routing algorithm in this task.

However, inspect the generated route and make sure the change does not conceal those limitations.

If a route is connected in the CTC layout but would be rejected by the Track Controller or Track Model because of direction or switch geometry, report that limitation accurately.

Do not claim a route to Edgebrook is executable merely because selecting a yard starting block made it possible to generate a schedule.

## 6. Preserve all existing system integration

The current dispatch integration is:

CTC → Track Controller → Track Model → Train Model

Train Model position → Track Model occupancy → Track Controller → CTC

Do not change this architecture.

Existing behavior to preserve:

- Canonical train IDs `001`–`010`
- Simulation-clock-controlled schedule release
- Dispatch request retries and acknowledgements
- Automatic Train Model activation
- Cumulative position reporting
- Multi-block occupancy
- CTC's anonymous occupancy-based location inference
- Movement suggestions and authority handoffs
- Dispatcher rerouting after a train has been released
- Three-line operation
- Default station dwell times and editable dwell times

The new starting-block selection should affect the **initial planned route and physical placement location**, not how the system subsequently tracks or controls the train.

## 7. Testing requirements

Add or update tests for:

**Starting-block selection**
- A line with one valid yard entry selects it correctly.
- A line with multiple yard entries permits choosing any eligible entry.
- A non-yard block cannot be selected or queued as a starting block.
- Each train in a multi-train schedule can have a different starting block.
- A selected block on another line is rejected.
- Missing yard-entry metadata produces a clear failure.

**Scheduling**
- Departure time is read from the selected start block.
- Intermediate route blocks are generated correctly.
- The route begins at the selected block.
- Existing arrival and dwell times continue working.
- Changing the start block does not silently corrupt a schedule.
- CSV imports use the same validation.
- A changed layout invalidates an obsolete start selection.

**Integration**
- CTC sends the selected `StartBlockId` in `TrainDispatchRequestMessage`.
- Track Controller forwards the existing request correctly.
- Track Model and Train Model activate the train at the selected start block.
- Position zero causes the selected starting block to become occupied.
- CTC detects the new occupancy and begins normal movement authorization.

Preserve all existing tests, including the recently added `PhysicalDispatchIntegrationTests` and `LivePhysicsEndToEndTests`.

If old test fixtures deliberately dispatch from arbitrary non-yard blocks, distinguish those isolated testing fixtures from the actual production yard-entry policy. Update affected tests appropriately without creating a production bypass that allows unrestricted dispatching.
