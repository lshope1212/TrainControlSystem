==================================================
WHY THE TEST UI EXISTS
==================================================

Eventually the complete system will contain separate modules such as:

- CTC
- Track Controller
- Track Model
- Train Controller
- Train Model

During individual CTC development, those other modules may not exist or may not yet be integrated.

The Test UI therefore needs to eventually simulate the modules connected to CTC.

For example:

SIMULATED INPUT:

Test UI
    ↓
creates BlockStatusMessage
    ↓
CTCService.ApplyBlockStatus(...)
    ↓
real CTC.Core state changes

SIMULATED OUTPUT:

dispatcher action in Test UI
    ↓
real CTCService method executes
    ↓
CTCService calls IMessageSender
    ↓
RecordingMessageSender captures the outgoing message
    ↓
Test UI displays the message

This is important:

The Test UI should NEVER duplicate CTC business logic.

All actual CTC behavior must remain in CTC.Core.

The Test UI's responsibilities are only:

1. collect manually entered simulated inputs,
2. construct the same TrainControl.Contracts messages the real modules will eventually send,
3. pass those messages into CTC.Core,
4. invoke public CTC functionality,
5. capture outgoing IMessageSender messages instead of using real inter-process communication,
6. display resulting CTC state and captured outputs.

==================================================
RECORDING MESSAGE SENDER
==================================================

This is the most important infrastructure piece.

CTCService currently depends on the CTC.Core IMessageSender abstraction.

The production CTC.Wpf project currently provides a NamedPipeMessageSender.

The Test UI must instead provide:

RecordingMessageSender

It should implement the existing CTC.Core.Interfaces.IMessageSender interface exactly as it currently exists in the repo.

Do not change IMessageSender merely to accommodate the Test UI unless there is an unavoidable reason.

RecordingMessageSender should NOT:

- open named pipes,
- communicate with Track Controller,
- serialize to a transport,
- send network/process messages.

Instead, SendAsync should capture the message passed to it.

Create a simple RecordedMessage model suitable for displaying captured messages.

At minimum, each captured message should provide:

- message type
- the actual message/payload object
- a timestamp or sequence number if useful
- a human-readable representation suitable for displaying in the Test UI

Prefer storing the actual strongly typed object/payload rather than only converting it to a string.

Expose the collection in a way that the MainWindowViewModel can display newly captured messages.

ObservableCollection<RecordedMessage> is acceptable if it fits the design.

Since the Test UI will initially run CTCService calls from the WPF UI thread, do not over-engineer thread synchronization at this stage. Keep the implementation straightforward, but structure it so it could be improved later.

DEPENDENCY COMPOSITION
==================================================

The production application currently conceptually does this:

The Test UI should instead compose:

Then construct MainWindowViewModel using the CTC service and recording sender.

Conceptually:

ICTCService ctcService = new CTCService(sender);

    ctcService,
    sender
);

Follow the actual constructors/interfaces found in the repository.

Do not introduce a dependency injection framework for this. Constructor injection is enough.
